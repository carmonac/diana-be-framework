Overview
Spring-inspired · Compile-time DI · Zero reflection

Build Dart backends the right way

Diana is a Spring-inspired, annotation-driven backend framework for Dart. Everything — dependency injection, routing, middleware wiring, validation — is resolved at compile time. No reflection, no runtime container. Configuration mistakes are build errors, and startup is instant.

Get Started Follow the Tutorial
⚡

Compile-Time DI

Dependency resolution, routing, and validation checked at build time. The runtime contains no reflection, no type maps, no resolution logic.

🔒

Type-Safe by Design

Generated code is plain typed Dart. The DI container is a class with typed fields in dependency order — debuggable with any IDE.

🚀

Instant Startup

No container bootstrap, no runtime scanning, no reflection warm-up. The generated composition root wires everything before your first line runs.

🧩

Feature-Rich

Controllers, middleware, validation, WebSockets, SSE, gRPC, authentication, persistence, OpenAPI, CORS — all with the same annotation-driven model.

📦

Modular Packages

Core runtime, generator, gRPC, auth, and persistence live in separate packages. You depend only on what you use.

🔧

Hot Reload

Watch mode regenerates on save. Handler bodies hot-reload with the VM service. DI-graph changes need a restart — clearly documented.

Getting Started

Go from an empty directory to a running HTTP server in 5 minutes.

1. Create a project

dart create -t console my_api
cd my_api

2. Add dependencies

# pubspec.yaml
dependencies:
  diana: ^0.6.0

dev_dependencies:
  build_runner: ^2.12.0
  diana_generator: ^0.6.0
Working inside the Diana monorepo? Add your package to the workspace: list of the root pubspec.yaml and use resolution: workspace instead of version constraints.

Run dart pub get.

3. Declare the application entrypoint

Every Diana application has exactly one class annotated with @DianaApplication, placed anywhere under lib/ (convention: lib/app.dart):

// lib/app.dart
import 'package:diana/diana.dart';

@DianaApplication()
class MyApp {}

The class body stays empty — it only anchors the generated code. The generator emits lib/app.diana_app.dart next to it.

4. Write a controller

Controllers declare routes with annotations. Libraries that declare routes need a part directive for their generated code:

// lib/controllers/hello_controller.dart
import 'package:diana/diana.dart';

part 'hello_controller.diana.dart';

@RestController('/hello')
class HelloController {
  @Get()
  Map<String, dynamic> hello() => {'message': 'Hello from Diana!'};

  @Get('/:name')
  String greet(@PathParam() String name) => 'Hello, $name!';
}

5. Generate

dart run build_runner build

This emits:

  • lib/controllers/hello_controller.diana.dart — the route adapters
  • lib/app.diana_app.dart — the composition root: DianaContext, buildDianaServer() and runDiana()

During development, use dart run build_runner watch to regenerate on save.

6. Run

// bin/server.dart
import 'package:my_api/app.diana_app.dart';

Future<void> main() => runDiana();
$ dart run bin/server.dart
[diana] Listening on http://0.0.0.0:8080

$ curl localhost:8080/hello
{"message":"Hello from Diana!"}

$ curl localhost:8080/hello/dart
Hello, dart!

The default address is 0.0.0.0:8080; override it with an application.yaml (server.host, server.port) or the environment variables SERVER_HOST / SERVER_PORT.

Architecture

How Diana works inside — from annotating a class to serving a request.

Design Principles

  1. Compile time over runtime. Anything that can fail — dependency resolution, binding compatibility, JSON contracts, handler signatures — is checked during code generation. The runtime contains no resolution logic, no maps of types, no reflection.
  2. Generated code is thin; semantics live in the runtime. Adapters and validators are one-liners calling tested runtime helpers. This keeps generated diffs small and the behaviour centrally testable.
  3. The HTTP engine is a detail. relic provides the server lifecycle, trie router and path-parameter extraction. It is confined to a single adapter file.
  4. Deterministic output. Same input, byte-identical output — sorted emission everywhere, no timestamps. Enables git diff --exit-code freshness checks.

Package Layout

packages/
├── diana_annotation    # const annotation classes; deps: meta only
├── diana               # runtime; deps: relic, yaml, xml; re-exports annotations
├── diana_generator     # builders; deps: analyzer, build, source_gen,
│                       # code_builder, dart_style, diana_annotation
├── diana_grpc          # gRPC runtime; deps: diana, grpc
├── diana_auth          # security; deps: diana, crypto
└── diana_data          # persistence; deps: diana, knex_dart

Boundary rules enforced by tests: each add-on package is the only one importing its respective dependency (relic, grpc, crypto, knex_dart). The generator imports none of the add-ons.

The Build Pipeline

Three builders, ordered by runs_before + required_inputs:

  1. diana_metadata — Per-library summaries. Regex pre-check skips irrelevant files. Annotated libraries are resolved into a LibrarySummary (injectables, controllers, routes, middleware, advices) written as JSON to the build cache.
  2. diana_part — Per-library code. Emits route adapters, validators, config binders. Local build-time validation lives here with exact source spans.
  3. diana_bootstrap — The aggregator. Runs on the @DianaApplication library only: collects all .diana.json files, resolves the DI graph (Kahn topological sort, DFS cycle extraction), validates middleware, and emits DianaContext, buildDianaServer(), runDiana().

The Runtime Pipeline

relic (trie router, HTTP server)
  └─ RelicAdapter: relic Request → DianaRequest, DianaResponse → relic Response
       └─ error boundary (ValidationException → 400, advice chain,
          HttpException → status, else opaque 500)
            └─ middleware chain: global → controller → route
                 └─ generated adapter: bind → validate → invoke → serialize
                      └─ your method

Composition happens once at route-registration time. Nothing is looked up per request.

Testing Strategy

  • Graph logic: table-driven tests over hand-built summaries
  • Builders: build_test with in-memory sources
  • Runtime: unit tests for config, binding, validation, pipeline ordering
  • End-to-end: the examples/todo_api suite boots the generated server
  • Boundary tests: fail if package:relic leaks outside the adapter
  • Determinism: build twice, compare checksums

Troubleshooting & FAQ

Build Problems

"Missing the part directive"

Paste the printed part 'xxx.diana.dart'; line into the named file, after the imports. Needed by libraries with controllers, constrained DTOs or @ConfigurationProperties classes.

Analyzer errors in *.diana.dart / *.diana_app.dart

Generated files can be stale. Re-run dart run build_runner build. If errors persist, check the build log for the real diagnostic.

runDiana / buildDianaServer doesn't exist

  • Is there exactly one @DianaApplication class under lib/?
  • Did the build run without severe errors?
  • Import path: package:<your_app>/<file>.diana_app.dart

Stale results / weird incremental behaviour

dart run build_runner clean
dart run build_runner build

Runtime Problems

App exits with ConfigException at startup

By design: a @Value without default or a required @ConfigurationProperties key is missing. The message names the key and the environment variable that can supply it.

application.yaml seems to be ignored

It's resolved against the working directory of the process, not the package root. Environment variables silently win over file values.

Every response is 404

The route path is controller path + method path. The generated buildDianaServer() lists every registered route — read it, it's short.

Port already in use

SERVER_PORT=0 dart run bin/server.dart binds a free one, or set server.port.

FAQ

Why compile-time DI instead of a runtime container?

Wiring errors surface in CI instead of production, startup does zero resolution work, the generated context is plain debuggable Dart, and tree-shaking keeps working because there's no reflection.

Does Diana use dart:mirrors or macros?

Neither. Diana generates code with build_runner, like riverpod or json_serializable.

Can I use it with Flutter?

Diana is a server-side framework. Share DTOs between a Diana backend and a Flutter app by putting them in a common package.

Can two apps live in one package?

No — one @DianaApplication per package (build error otherwise). Use separate packages in the workspace.

Is there hot reload?

Yes: dart run build_runner watch + dart run --enable-vm-service bin/server.dart. Handler bodies hot-reload; DI-graph changes need a restart.

3. Dependency Injection

The DTO:

// lib/dto/book_dto.dart
class BookDto {
  final int id;
  final String title;
  final String author;

  const BookDto({required this.id, required this.title, required this.author});

  factory BookDto.fromJson(Map<String, dynamic> json) => BookDto(
        id: json['id'] as int,
        title: json['title'] as String,
        author: json['author'] as String,
      );

  Map<String, dynamic> toJson() =>
      {'id': id, 'title': title, 'author': author};
}

Repository and service:

// lib/repositories/book_repository.dart
import 'package:diana/diana.dart';
import '../dto/book_dto.dart';

abstract interface class BookRepository {
  List<BookDto> findAll({int limit});
  BookDto? find(int id);
  BookDto save(String title, String author);
}

@Repository()
class InMemoryBookRepository implements BookRepository {
  final _books = <int, BookDto>{
    1: const BookDto(id: 1, title: 'Dart in Action', author: 'M. Ford'),
  };
  int _nextId = 2;

  @override
  List<BookDto> findAll({int limit = 20}) =>
      _books.values.take(limit).toList();

  @override
  BookDto? find(int id) => _books[id];

  @override
  BookDto save(String title, String author) {
    final book = BookDto(id: _nextId++, title: title, author: author);
    _books[book.id] = book;
    return book;
  }
}
// lib/services/book_service.dart
import 'package:diana/diana.dart';
import '../dto/book_dto.dart';
import '../repositories/book_repository.dart';

@Service()
class BookService {
  final BookRepository repo;
  BookService(this.repo);

  List<BookDto> list(int limit) => repo.findAll(limit: limit);
}

Inject into the controller:

@RestController('/books')
class BookController {
  final BookService service;
  BookController(this.service);

  @Get()
  List<BookDto> list() => service.list(20);
}

Dependency Injection

Diana's DI is resolved entirely at build time. Missing providers, ambiguous bindings, cycles and scope violations are build errors.

Declaring Providers

@Service()        // business logic
class TodoService { ... }

@Repository()     // data access
class InMemoryTodoRepository implements TodoRepository { ... }

@Component()      // anything else
class Clock { ... }

@Injectable(scope: Scope.transient)
class UuidFactory { ... }

@Service, @Repository and @Component are semantic aliases of @Injectable — same parameters (scope, as, name), identical behaviour.

Provider Requirements

  • Public (not _Private)
  • Concrete (not abstract)
  • No type parameters
  • A public unnamed generative constructor
  • One role annotation per class

How Dependencies Resolve

For each constructor parameter, Diana looks up a provider by exact type in two tiers:

  1. Strong bindings — the provider's own class, plus the type named by as:
  2. Auto-binding candidates — every supertype (transitively, excluding dart:*)

Strong bindings win. Within a tier: one match → resolved; multiple → build error; none → missing provider error.

Several Implementations

as: — declare one the binding:

@Repository(as: TodoRepository)
class PostgresTodoRepository implements TodoRepository { ... }

Qualifiers — name and select:

@Component(name: 'smtp')
class SmtpSender implements MailSender { ... }

@Service()
class Notifier {
  Notifier(@Named('smtp') this.sender);
  final MailSender sender;
}

Scopes

ScopeLifetimeGenerated as
singleton (default)One instancelate final on DianaContext
requestPer HTTP requestlate final on DianaRequestScope
transientPer injection pointFactory method

Rules: nothing reachable from a singleton may be request-scoped. Middleware must be singletons.

What Gets Generated

class DianaContext {
  DianaContext(this.config);
  final DianaConfig config;

  late final InMemoryTodoRepository inMemoryTodoRepository =
      InMemoryTodoRepository();

Controllers & Routing

Annotated route methods become adapters that bind, validate, invoke and serialize — your code stays plain Dart.

Declaring Routes

import 'package:diana/diana.dart';
part 'todo_controller.diana.dart';

@RestController('/todos')
class TodoController {
  final TodoService service;
  TodoController(this.service);

  @Get()
  List<TodoDto> list(@QueryParam('limit', '20') int limit) =>
      service.list(limit);

  @Get('/:id')
  TodoDto getById(@PathParam() int id) => service.getOrThrow(id);

  @Post()
  @ResponseStatus(201)
  TodoDto create(@Body() CreateTodoRequest body) => service.create(body);

  @Delete('/:id')
  void remove(@PathParam() int id) => service.delete(id);
}
  • @RestController([path, scope]) — mounts all routes under path
  • @Get, @Post, @Put, @Delete, @Patch — optional path relative to controller
  • Paths use :name segments; trie-based matching, order-independent
  • @HttpRoute('HEAD', '/status') for methods without a shorthand

Under the Hood

For each route the generator emits a public adapter:

Future<DianaResponse> $diana$TodoController$create(
    TodoController c, DianaRequest req) async {
  final $a0 = CreateTodoRequest.fromJson(await decodeJsonMapBody(req));
  const $CreateTodoRequestValidator().validate($a0).throwIfInvalid();

Middleware

Intercept requests around handlers — logging, auth, headers, rate limiting.

The Interface

abstract interface class Middleware {
  FutureOr<DianaResponse> handle(DianaRequest request, Next next);
}

typedef Next = FutureOr<DianaResponse> Function(DianaRequest request);

Call next(request) to continue; return a response directly to short-circuit.

Global Middleware

@GlobalMiddleware(order: 0)
class TimingMiddleware implements Middleware {
  @override
  Future<DianaResponse> handle(DianaRequest request, Next next) async {
    final watch = Stopwatch()..start();
    final response = await next(request);
    return response.copyWith(headers: {
      ...response.headers,
      'x-response-time-ms': '${watch.elapsedMilliseconds}',
    });
  }
}

Lower order runs first (outermost); ties broken by class name.

Per-Controller / Per-Route Middleware

@Component()
class ApiKeyMiddleware implements Middleware {
  ApiKeyMiddleware(@Value('app.apiKey') this.expected);
  final String expected;

  @override
  Future<DianaResponse> handle(DianaRequest request, Next next) async {
    if (request.header('x-api-key') != expected) {
      return DianaResponse.json({'error': 'unauthorized'}, statusCode: 401);
    }
    return await next(request);
  }
}

@RestController('/admin')
@UseMiddleware([AuditMiddleware])
class AdminController {
  @Delete('/:id')
  @UseMiddleware([ApiKeyMiddleware])
  void remove(@PathParam() int id) { ... }
}

Execution Order

global (sorted by order) → controller-level → route-level → handler

The first middleware sees the request first and the response last (onion model).

Passing Data to Handlers

Use DianaRequest.attributes:

// handler

    {'userId': req.attributes['userId']};

Validation

Constraint annotations on DTO fields become generated validators that run before your handler.

Declaring Constraints

import 'package:diana/diana.dart';
part 'signup_request.diana.dart';

class SignupRequest {
  @NotBlank(message: 'name is required')
  @Size(min: 2, max: 50)
  final String name;

  @Email()
  final String email;

  @Min(18)
  @Max(130)
  final int? age;

  @Valid()
  final Address? address;
}

Error Handling

Every request runs inside Diana's exception boundary. Unrecognized exceptions become opaque 500s.

The Pipeline

  1. ValidationException → 400 with structured field map
  2. @ControllerAdvice handlers — most specific subtype first
  3. HttpException hierarchy → its status code
  4. Anything else → 500 {"error": "internal_server_error"}

  DianaResponse onBookNotFound(BookNotFound e, DianaRequest req) =>
      DianaResponse.json(
        {'error': 'book_not_found', 'id': e.id, 'path': req.path},
        statusCode: 404,
      );
}

Handlers also catch subtypes. Most specific type wins. Multiple advice classes merge into one chain.

WebSockets

Implement a handler, annotate with a path, and Diana wires the upgrade, lifecycle callbacks and DI.

Basic Usage

import 'package:diana/diana.dart';

@WebSocketController('/ws/echo')
class EchoHandler extends BaseWebSocketHandler {
  @override
  void onOpen(WebSocketSession session) =>
      session.sendText('welcome');

  @override
  void onMessage(WebSocketSession session, WebSocketMessage message) {
    if (message is TextMessage) session.sendText(message.text);
  }
}

Handler Lifecycle

CallbackWhen
onOpen(session)Connection established
onMessage(session, message)Frame arrived (TextMessage or BinaryMessage)
onError(session, error, stackTrace)Transport error / callback exception
onClose(session, code, reason)Connection closed; always called last

Handler Scope

  • Scope.singleton (default) — one shared handler for all connections
  • Scope.transient — fresh handler per connection (instance fields = per-connection state)
  • Scope.request — build error

Handshake Interceptors

@UseMiddleware on a WebSocketController runs middleware on the handshake request:

@WebSocketController('/ws/chat/:room')
@UseMiddleware([ApiKeyMiddleware])
class ChatHandler extends BaseWebSocketHandler {
  @override
  void onOpen(WebSocketSession session) {
    final user = session.attributes['user']; // set by middleware
  }
}

Global middleware do not apply to handshakes — interceptors are explicit opt-in.

Application Lifecycle

Explicit lifecycle: build → initialize → serve → shutdown → dispose.

@PostConstruct / @PreDestroy

@Repository()
class Db {
  late final Connection _conn;

  @PostConstruct()
  Future<void> connect() async => _conn = await Connection.open(...);

  @PreDestroy()
  Future<void> disconnect() => _conn.close();
}

Rules: public instance method, no parameters, void or Future<void>, at most one of each per class, singleton only.

  • initialize() constructs singletons in dependency order, awaits @PostConstruct
  • dispose() runs @PreDestroy in reverse dependency order

Graceful Shutdown

runDiana() installs SIGINT/SIGTERM handlers. On signal: stop accepting, drain, dispose.

final app = await buildDianaApp(config: ..., overrides: ...);
app.context;   // the DI container
app.server;    // the DianaServer
await app.initialize();
await app.server.serve(port: 0);
await app.server.close();
await app.dispose();

Application Events

Publish plain Dart objects as events; singleton providers react via @EventListener.

Declaring a Listener

class TodoCreated {
  final int id;
  final String title;
  const TodoCreated(this.id, this.title);
}

@Component()
class TodoAuditListener {
  @EventListener()
  void onTodoCreated(TodoCreated event) => log(event.title);
}

Matching is by type, subtypes included. Request-scoped and transient providers cannot listen.

Publishing

@Service()
class TodoService {
  final DianaEventPublisher publisher;
  TodoService(this.publisher);

  Future<TodoDto> create(CreateTodoRequest request) async {
    final todo = repo.save(request.title);
    await publisher.publish(TodoCreated(todo.id, todo.title));
    return todo;
  }
}

publish runs every matching listener in registration order, awaited, before returning.

Content Negotiation

Routes can accept and produce formats beyond JSON — XML out of the box, anything via pluggable codecs.

Registering a Codec

@Component()
class AppXmlCodec extends XmlCodec {}

Custom formats implement BodyCodec:

@Component()
class CsvCodec implements BodyCodec {
  @override
  List<String> get mimeTypes => ['text/csv'];

  @override
  Object? decode(String body) { /* → Map/List/scalars */ }

  @override
  String encode(Object? value) { /* Map/List/scalars → wire */ }
}

@Consumes / @Produces

@Post('/xml')
@Consumes(['application/xml'])
@Produces(['application/xml', 'application/json'])
TodoDto create(@Body() CreateTodoRequest body) => service.create(body);
  • @Consumes — request Content-Type must match or 415
  • @Produces — first type matching Accept header wins; nothing acceptable → 406
  • Both are projected into the generated OpenAPI document

Authentication & Authorization

Pluggable strategies, injectable principal, and @Secured / @RolesAllowed guards. Lives in diana_auth.

Assembly

@GlobalMiddleware(order: -100)
class AppAuth extends AuthenticationMiddleware {
  AppAuth(@Value('auth.jwt.secret') String secret)
    : super(authenticators: [
        JwtAuthenticator(Hs256TokenVerifier(secret)),
        ApiKeyAuthenticator(myKeyStore),
      ]);
}

Strategies run in order; first to recognize credentials wins. No credentials → anonymous (guards enforce access).

Built-in Strategies

  • JWT — Authorization: Bearer <token>, HS256 hardened (no alg: none, constant-time comparison)
  • HTTP Basic — via UserStore interface
  • API Key — header-based via ApiKeyValidator

Authorizing Routes

@RestController('/admin')
@Secured()
class AdminController {
  @Get('/stats')
  Stats stats() => ...;

  @Delete('/users/:id')
  @RolesAllowed(['admin'])
  void deleteUser(@PathParam() int id) => ...;
}
  • @Secured() → 401 for anonymous
  • @RolesAllowed([...]) → 401 anonymous, 403 if principal lacks every listed role

Reading the Principal

@Get('/me')
@Secured()
Profile me(@Principal() AuthPrincipal user) =>
    Profile(user.name, user.roles);

Determinism

  • Sorted emission everywhere (topological, by name, by path)
  • No timestamps or random values
  • Optional features emitted only when used
  • CI can enforce with git diff --exit-code

Build Diagnostics

Every error diana_generator can report, grouped by area.

Class-level Rules

  • One role annotation per class
  • Must be public, concrete, no type parameters
  • Must have public unnamed generative constructor
  • as: target must be implemented

Dependency Graph

  • No provider found — annotate a providing class or check type/qualifier
  • Multiple providers — disambiguate with @Named or as:
  • Dependency cycle — restructure to break the cycle
  • Scope violation — singleton depending on request-scoped

Controllers & Routes

  • Public instance methods only
  • Exactly one binding annotation per parameter
  • Supported types: String, int, double, bool, num
  • DTO must have fromJson for @Body, toJson for returns
  • Missing part directive — exact line printed

Common Fixes

  • Stale generated files → dart run build_runner clean && dart run build_runner build
  • Missing @DianaApplication → exactly one per package
  • Import prefix on route types → import without prefix in controller libraries
