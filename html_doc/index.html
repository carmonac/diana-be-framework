Overview
Spring-inspired · Compile-time DI · Zero reflection

Build Dart backends the right way

Diana is a Spring-inspired, annotation-driven backend framework for Dart. Everything — dependency injection, routing, middleware wiring, validation — is resolved at compile time. No reflection, no runtime container. Configuration mistakes are build errors, and startup is instant.

⚡

Compile-Time DI

Dependency resolution, routing, and validation checked at build time. The runtime contains no reflection, no type maps, no resolution logic.

🔒

Type-Safe by Design

Generated code is plain typed Dart. The DI container is a class with typed fields in dependency order — debuggable with any IDE.

🚀

Instant Startup

No container bootstrap, no runtime scanning, no reflection warm-up. The generated composition root wires everything before your first line runs.

🧩

Feature-Rich

Controllers, middleware, validation, WebSockets, SSE, gRPC, authentication, persistence, OpenAPI, CORS — all with the same annotation-driven model.

📦

Modular Packages

Core runtime, generator, gRPC, auth, and persistence live in separate packages. You depend only on what you use.

🔧

Hot Reload

Watch mode regenerates on save. Handler bodies hot-reload with the VM service. DI-graph changes need a restart — clearly documented.

Getting started

This page takes you from an empty directory to a running HTTP server. For a full walkthrough of every feature, continue with the tutorial.

1. Create a project

dart create -t console my_api
cd my_api

2. Add dependencies

# pubspec.yaml
dependencies:
  diana: ^0.6.0

dev_dependencies:
  build_runner: ^2.12.0
  diana_generator: ^0.6.0
Working inside the Diana monorepo? Add your package to the workspace: list of the root pubspec.yaml and use resolution: workspace instead of version constraints.

Run dart pub get.

3. Declare the application entrypoint

Every Diana application has exactly one class annotated with @DianaApplication, placed anywhere under lib/ (convention: lib/app.dart):

// lib/app.dart
import 'package:diana/diana.dart';

@DianaApplication()
class MyApp {}

The class body stays empty — it only anchors the generated code. The generator emits lib/app.diana_app.dart next to it.

4. Write a controller

Controllers declare routes with annotations. Libraries that declare routes need a part directive for their generated code:

// lib/controllers/hello_controller.dart
import 'package:diana/diana.dart';

part 'hello_controller.diana.dart';

@RestController('/hello')
class HelloController {
  @Get()
  Map<String, dynamic> hello() => {'message': 'Hello from Diana!'};

  @Get('/:name')
  String greet(@PathParam() String name) => 'Hello, $name!';
}

5. Generate

dart run build_runner build

This emits:

  • lib/controllers/hello_controller.diana.dart — the route adapters
  • lib/app.diana_app.dart — the composition root: DianaContext,

buildDianaServer() and runDiana()

During development, use dart run build_runner watch to regenerate on save.

6. Run

// bin/server.dart
import 'package:my_api/app.diana_app.dart';

Future<void> main() => runDiana();
$ dart run bin/server.dart
[diana] Listening on http://0.0.0.0:8080

$ curl localhost:8080/hello
{"message":"Hello from Diana!"}

$ curl localhost:8080/hello/dart
Hello, dart!

The default address is 0.0.0.0:8080; override it with an application.yaml (server.host, server.port) or the environment variables SERVER_HOST / SERVER_PORT — see Configuration.

3. Dependency injection

Diana instantiates your classes through their constructors and resolves every parameter at build time. Let's add a data layer.

The DTO (plain Dart, JSON by convention — see JSON serialization):

// lib/dto/book_dto.dart
class BookDto {
  final int id;
  final String title;
  final String author;

  const BookDto({required this.id, required this.title, required this.author});

  factory BookDto.fromJson(Map<String, dynamic> json) => BookDto(
        id: json['id'] as int,
        title: json['title'] as String,
        author: json['author'] as String,
      );

  Map<String, dynamic> toJson() =>
      {'id': id, 'title': title, 'author': author};
}

A repository interface with an in-memory implementation:

// lib/repositories/book_repository.dart
import 'package:diana/diana.dart';

import '../dto/book_dto.dart';

abstract interface class BookRepository {
  List<BookDto> findAll({int limit});
  BookDto? find(int id);
  BookDto save(String title, String author);
}

@Repository()
class InMemoryBookRepository implements BookRepository {
  final _books = <int, BookDto>{
    1: const BookDto(id: 1, title: 'Dart in Action', author: 'M. Ford'),
  };
  int _nextId = 2;

  @override
  List<BookDto> findAll({int limit = 20}) =>
      _books.values.take(limit).toList();

  @override
  BookDto? find(int id) => _books[id];

  @override
  BookDto save(String title, String author) {
    final book = BookDto(id: _nextId++, title: title, author: author);
    _books[book.id] = book;
    return book;
  }
}

A service that depends on the interface:

// lib/services/book_service.dart
import 'package:diana/diana.dart';

import '../dto/book_dto.dart';
import '../repositories/book_repository.dart';

@Service()
class BookService {
  final BookRepository repo;

  BookService(this.repo);

  List<BookDto> list(int limit) => repo.findAll(limit: limit);
}

BookService asks for BookRepository; InMemoryBookRepository is the only provider implementing it, so Diana auto-binds them. If you later add a second implementation, the build fails with an ambiguity error and tells you to pick one with @Named or as: — see Dependency injection.

Inject the service into the controller and add a real route:

@RestController('/books')
class BookController {
  final BookService service;

  BookController(this.service);

  @Get()
  List<BookDto> list() => service.list(20);
}

Rebuild and try it:

$ dart run build_runner build && dart run bin/server.dart
$ curl localhost:8080/books
[{"id":1,"title":"Dart in Action","author":"M. Ford"}]

Peek at lib/app.diana_app.dart to see what the generator wired:

class DianaContext {
  DianaContext(this.config);
  final DianaConfig config;
  late final InMemoryBookRepository inMemoryBookRepository =
      InMemoryBookRepository();
  late final BookService bookService = BookService(inMemoryBookRepository);
  late final BookController bookController = BookController(bookService);
}

This class is the DI container — plain typed fields in dependency order. No maps, no reflection, nothing to misconfigure at runtime.

4. Path and query parameters

// in BookController
@Get()
List<BookDto> list(@QueryParam('limit', '20') int limit) =>
    service.list(limit);

@Get('/:id')
BookDto getById(@PathParam() int id) => service.getOrThrow(id);

And in BookService:

BookDto getOrThrow(int id) =>
    repo.find(id) ?? (throw NotFoundException('No book with id $id.'));

Parameter binding rules (full list in Controllers and routing):

  • @PathParam() binds :id from the route; the name defaults to the Dart

parameter name. Path parameters must be non-nullable.

  • @QueryParam('limit', '20') binds ?limit=; the second positional

argument is the default (always written as a string). A nullable type (int?) makes the parameter optional instead.

  • Values convert to String, int, double, bool or num. A failed

conversion is an automatic 400 — no code on your part:

$ curl localhost:8080/books/abc
{"error":"bad_request","message":"Path parameter 'id' must be int, got 'abc'."}

NotFoundException is one of Diana's built-in HTTP exceptions — thrown anywhere during a request, it becomes a JSON response with its status code:

$ curl localhost:8080/books/99
{"error":"not_found","message":"No book with id 99."}

5. Request bodies and validation

Create a request DTO with constraint annotations. Libraries whose classes carry constraints also need a part directive (the generator writes a validator there):

// lib/dto/create_book_request.dart
import 'package:diana/diana.dart';

part 'create_book_request.diana.dart';

class CreateBookRequest {
  @NotBlank(message: 'title is required')
  @Size(max: 200)
  final String title;

  @NotBlank()
  final String author;

  CreateBookRequest({required this.title, required this.author});

  factory CreateBookRequest.fromJson(Map<String, dynamic> json) =>
      CreateBookRequest(
        title: json['title'] as String? ?? '',
        author: json['author'] as String? ?? '',
      );

  Map<String, dynamic> toJson() => {'title': title, 'author': author};
}

The route:

// in BookController
@Post()
@ResponseStatus(201)
BookDto create(@Body() CreateBookRequest body) => service.create(body);
// in BookService
BookDto create(CreateBookRequest request) =>
    repo.save(request.title, request.author);

The generated adapter decodes the JSON body, builds the DTO with fromJson, runs the generated validator, and only then calls your method. You never see an invalid object:

$ curl -X POST localhost:8080/books -H 'Content-Type: application/json' \
       -d '{"title": "Effective Dart", "author": "The Dart Team"}'
{"id":2,"title":"Effective Dart","author":"The Dart Team"}     # 201

$ curl -X POST localhost:8080/books -H 'Content-Type: application/json' \
       -d '{"title": "   "}'
{"error":"validation_failed","fields":{"title":["title is required"],"author":["must not be blank"]}}

Malformed JSON is a 400, and a non-JSON content type is a 415 — automatically. All constraints and the cascade rules (@Valid) are in the validation guide.

6. Domain errors and @ControllerAdvice

Built-in exceptions are convenient, but a domain layer usually shouldn't know about HTTP. Define a domain error:

// lib/errors/book_not_found.dart
class BookNotFound implements Exception {
  final int id;
  const BookNotFound(this.id);
}

Throw it from the service instead of NotFoundException:

BookDto getOrThrow(int id) => repo.find(id) ?? (throw BookNotFound(id));

And map it to HTTP in one place:

// lib/advice/error_advice.dart
import 'package:diana/diana.dart';

import '../errors/book_not_found.dart';

@ControllerAdvice()
class ErrorAdvice {
  @ExceptionHandler(BookNotFound)
  DianaResponse onBookNotFound(BookNotFound e, DianaRequest req) =>
      DianaResponse.json(
        {'error': 'book_not_found', 'id': e.id, 'path': req.path},
        statusCode: 404,
      );
}
$ curl localhost:8080/books/99
{"error":"book_not_found","id":99,"path":"/books/99"}

Handlers are selected by exception type, most specific subtype first. Any exception nothing handles becomes an opaque 500 — internals never leak to clients. Details in Error handling.

7. Middleware

Middleware wrap request handling, Spring-interceptor style. A global one that times every request:

// lib/middleware/timing_middleware.dart
import 'package:diana/diana.dart';

@GlobalMiddleware(order: 0)
class TimingMiddleware implements Middleware {
  @override
  Future<DianaResponse> handle(DianaRequest request, Next next) async {
    final watch = Stopwatch()..start();
    final response = await next(request);
    return response.copyWith(headers: {
      ...response.headers,
      'x-response-time-ms': '${watch.elapsedMilliseconds}',
    });
  }
}

And a guard applied to a single route. Middleware are regular injectable components — constructor injection (including @Value, next section) works:

// lib/middleware/admin_guard.dart
import 'package:diana/diana.dart';

@Component()
class AdminGuard implements Middleware {
  final String apiKey;

  AdminGuard(@Value('app.adminKey', defaultValue: 'changeme') this.apiKey);

  @override
  Future<DianaResponse> handle(DianaRequest request, Next next) async {
    if (request.header('x-api-key') != apiKey) {
      return DianaResponse.json({'error': 'unauthorized'}, statusCode: 401);
    }
    return await next(request);
  }
}

Apply it with @UseMiddleware (works on a method or on the whole controller):

@Post()
@ResponseStatus(201)
@UseMiddleware([AdminGuard])
BookDto create(@Body() CreateBookRequest body) => service.create(body);
$ curl -X POST localhost:8080/books -d '{}'                      # 401
$ curl -s -D - -o /dev/null localhost:8080/books | grep x-response-time
x-response-time-ms: 0

Execution order is always *global (by order) → controller-level → route-level → handler*, and returning without calling next short-circuits the chain. See Middleware.

Create application.yaml in the project root:

Nested keys flatten to dot-keys (app.adminKey), and any key can be overridden by the corresponding environment variable — dots become underscores, upper-cased:

$ SERVER_PORT=9000 APP_ADMINKEY=other dart run bin/server.dart

You've already used @Value in AdminGuard. To bind a whole section as a typed object, use @ConfigurationProperties (also needs a part directive):

// lib/config/app_info.dart
import 'package:diana/diana.dart';

part 'app_info.diana.dart';

@ConfigurationProperties('app.info')
class AppInfo {
  final String name;
  final String version;

  const AppInfo({required this.name, required this.version});
}

The class becomes injectable like any other component:

@RestController('/info')
class InfoController {
  final AppInfo info;
  InfoController(this.info);

  @Get()
  Map<String, dynamic> get() => {'name': info.name, 'version': info.version};
}

A required key that's missing from every source fails at startup with a message naming both the key and the environment variable that could supply it. See Configuration.

9. Testing

The generated buildDianaServer() accepts a config override and can bind to an ephemeral port — ideal for end-to-end tests without touching the real application.yaml:

// test/api_test.dart
import 'dart:convert';
import 'dart:io';

import 'package:bookstore/app.diana_app.dart';
import 'package:diana/diana.dart';
import 'package:test/test.dart';

void main() {
  late DianaServer server;
  late int port;

  setUpAll(() async {
    server = await buildDianaServer(
      config: DianaConfig({'app.adminKey': 'test-key'}),
    );
    await server.serve(port: 0, quiet: true); // OS-assigned port
    port = server.port!;
  });

  tearDownAll(() => server.close());

  test('lists the seeded book', () async {
    final client = HttpClient();
    final req =
        await client.getUrl(Uri.parse('http://127.0.0.1:$port/books'));
    final res = await req.close();
    final body = jsonDecode(await res.transform(utf8.decoder).join());
    expect(res.statusCode, 200);
    expect(body, hasLength(1));
    client.close();
  });
}

For plain unit tests of your object graph — no HTTP — use the generated buildDianaContext():

final ctx = buildDianaContext();
expect(ctx.bookService.list(10), hasLength(1));

More patterns (unit-testing middleware, validators, config) in the testing guide.

Architecture

How Diana works inside. Useful for contributors and for anyone who wants to understand exactly what happens between annotating a class and serving a request.

Design principles

  1. Compile time over runtime. Anything that can fail — dependency

resolution, binding compatibility, JSON contracts, handler signatures — is checked during code generation. The runtime contains no resolution logic, no maps of types, no reflection.

  1. Generated code is thin; semantics live in the runtime. Adapters and

validators are one-liners calling tested runtime helpers (bindQueryParam, checkNotBlank, …). This keeps generated diffs small and the behaviour centrally testable.

  1. The HTTP engine is a detail. relic

provides the server lifecycle, trie router and path-parameter extraction. It is confined to a single adapter file; a test greps the runtime package to enforce that nothing else imports it.

  1. Deterministic output. Same input, byte-identical output — sorted

emission everywhere, no timestamps. Enables git diff --exit-code freshness checks.

Package layout

packages/
├── diana_annotation    # const annotation classes; deps: meta only
├── diana               # runtime; deps: relic, yaml, xml; re-exports annotations
├── diana_generator     # builders; deps: analyzer, build, source_gen,
│                       # code_builder, dart_style, diana_annotation
│                       # (NOT diana — keeps relic out of the build chain)
├── diana_grpc          # gRPC runtime; deps: diana, grpc — the ONLY
│                       # package importing package:grpc
├── diana_auth          # security; deps: diana, crypto — the ONLY
│                       # package importing package:crypto
└── diana_data          # persistence; deps: diana, knex_dart — the ONLY
                        # package importing package:knex_dart

diana_generator depends only on diana_annotation, so the build-time transitive closure stays free of the HTTP stack. Boundary rules enforced by tests: package:relic is imported only by diana/src/adapter/relic_adapter.dart; package:grpc only by diana_grpc; package:crypto only by diana_auth; package:knex_dart only by diana_data; and the generator imports none of the add-ons (it references DianaGrpcServer, SecuredGuard, Database, the $Tx$ proxies etc. by import-URL string, so apps depend only on the add-ons they use).

The build pipeline

Three builders, declared in packages/diana_generator/build.yaml with auto_apply: dependents (users only add the package to dev_dependencies):

lib/foo.dart ──▶ diana_metadata ──▶ foo.diana.json      (cache, hidden)
lib/foo.dart ──▶ diana_part     ──▶ foo.diana.dart      (source, part file)
lib/app.dart ──▶ diana_bootstrap──▶ app.diana_app.dart  (source, library)
                       ▲
                       └── reads every *.diana.json in the package

Phase ordering is guaranteed by runs_before + required_inputs: ['.diana.json'] on the bootstrap builder.

1. diana_metadata — per-library summaries

For each library, a cheap regex pre-check (does the source even mention a Diana annotation?) avoids resolving irrelevant files. Annotated libraries are resolved with the analyzer and read into a **plain-data LibrarySummary** (src/model/summary.dart): injectables (with scope, qualifier, as: binding, supertypes and constructor parameters as serializable TypeRefs), controllers and routes, global middleware, advices and the @DianaApplication entry. The summary is written as JSON to the build cache.

TypeRef = {libraryUri, name, typeArgs, nullable} — its key (nullability excluded) is the identity used for provider matching, which is why fully-instantiated generic dependencies match structurally.

2. diana_part — per-library code

Emits the part file: route adapters, validators, config binders (see the generated-code reference). All local build-time validation lives here so errors carry exact source spans: binding annotation rules, fromJson/toJson contract checks, constraint applicability, the missing-part-directive error.

Part files were chosen over standalone libraries for local artifacts because they share the host library's imports — generated code references user types exactly as written, with zero import management. The trade-off (users must write one part line) is softened by an error message containing the exact line to paste.

3. diana_bootstrap — the aggregator

Runs on the @DianaApplication library only:

  1. Collects every .diana.json (sorted by path for determinism).
  2. Resolves the graph (src/graph/di_graph.dart — pure functions over

summaries, no analyzer, no build system): indexes strong bindings (self type, as:) and auto-binding candidates (supertypes); resolves each constructor parameter; Kahn topological sort; DFS cycle extraction for readable cycle paths; scope analysis (request-reachability); every problem accumulated and reported together.

  1. Validates middleware references (injectable, implements Middleware,

singleton) and entrypoint uniqueness.

  1. Emits with code_builder (its prefixing allocator manages imports

across arbitrary user libraries) + dart_style: DianaContext, optional DianaRequestScope, _mapException (advice chain ordered by exception-type specificity, computed as supertype-chain depth at metadata time), buildDianaContext, buildDianaServer, runDiana.

Why summaries instead of resolving everything in the aggregator?

Incrementality and cost: build_runner re-runs the metadata builder only for changed libraries; the aggregator reads tiny JSON files instead of re-resolving the whole package. The plain-data boundary also isolates analyzer API churn (a historically unstable API) to the readers/ directory — graph logic and emitters never see analyzer types.

The runtime pipeline

relic (trie router, HTTP server)
  └─ RelicAdapter: relic Request → DianaRequest, DianaResponse → relic Response
       └─ error boundary (ValidationException → 400, advice chain,
          HttpException → status, else opaque 500)
            └─ middleware chain: global → controller → route
                 └─ generated adapter: bind → validate → invoke → serialize
                      └─ your method

Composition happens once, at route-registration time (DianaServer. register folds the chain into a single DianaHandler); nothing is looked up per request. Diana composes middleware itself rather than using the engine's mechanism so that the three-level ordering is deterministic and middleware get DI.

Two pieces of server state travel on the request rather than being read from configuration by generated code: DianaRequestLimits and the BodyCodecRegistry (discovered BodyCodec singletons). This keeps the generated adapter signature at (controller, request) and generated code free of config lookups.

WebSocket endpoints bypass the HTTP pipeline: the adapter answers the handshake with the engine's upgrade result and pumps the socket's event stream into the handler's onOpen/onMessage/onError/onClose callbacks, wrapping the engine socket in Diana's WebSocketSession.

Streamed responses (DianaResponse.bodyStream, used by SSE) also bypass the engine's response path: dart:io buffers small writes, which would hold SSE events back, so the adapter hijacks the socket (relic's Hijack result) and writes the HTTP/1.1 head plus chunked frames itself — unbuffered, with client disconnects propagated as a cancel of the source stream.

gRPC services don't route through this pipeline at all: DianaGrpcServer (package diana_grpc) runs package:grpc's own server on a separate port, sharing only the DI graph, configuration and lifecycle (served on initialize(), shut down first on dispose()).

Security (package diana_auth) reuses the middleware pipeline rather than adding a new mechanism: an AuthenticationMiddleware establishes the principal in request.attributes, and @Secured/@RolesAllowed compile to guard middleware the bootstrap appends last in each route's chain (after authentication, before the handler). The principal-attribute contract (principalAttributeKey + bindPrincipal) lives in package:diana so generated part-file adapters read it without importing diana_auth. gRPC — which has no request-attribute channel — is covered by a package:grpc interceptor the bootstrap wires from the same AuthenticationMiddleware.

Persistence (package diana_data) follows the same add-on shape: the generator emits a Database field on the context (opened/closed with the lifecycle) and, for @Transactional methods, a $Tx$ proxy subclass that wraps the call in an ambient transaction bound to the current Zone. knex_dart never reaches the core; the driver package is the user's.

  • Graph logic: table-driven tests over hand-built summaries, asserting

exact error strings — diagnostics are a feature, message regressions are test failures.

  • Builders: build_test's testBuilder/testBuilders with in-memory

  • Runtime: unit tests for config, binding, validation, pipeline

  • Boundary tests: fail if package:relic leaks outside the adapter or

  • Determinism: build twice, compare checksums (both examples).

Dependency injection

Diana's DI is resolved entirely at build time. The generator reads your annotated classes, resolves the full dependency graph, and emits a DianaContext class whose typed fields are the container. Missing providers, ambiguous bindings, dependency cycles and scope violations are build errors with precise locations — they cannot reach production.

Declaring providers

Annotate a class with any of the injectable annotations:

@Service()            // business logic
class TodoService { ... }

@Repository()         // data access
class InMemoryTodoRepository implements TodoRepository { ... }

@Component()          // anything else
class Clock { ... }

@Injectable(scope: Scope.transient)   // the general form
class UuidFactory { ... }

@Service, @Repository and @Component are semantic aliases of @Injectable — they accept the same parameters (scope, as, name) and behave identically. Pick whichever communicates intent.

Controllers (@RestController), middleware (@GlobalMiddleware), advices (@ControllerAdvice) and configuration classes (@ConfigurationProperties) are also providers and join the same graph.

Requirements for provider classes

  • Public (not _Private) — generated wiring references them across

libraries.

  • Concrete (not abstract).
  • No type parameters (class Repo<T> is rejected; provide a concrete

subclass).

  • A public unnamed generative constructor — Diana instantiates through

it. Every constructor parameter (positional or named) is resolved from the graph, except @Value parameters, which come from configuration.

  • One role annotation per class (@Service + @RestController on the same

class is a build error).

How dependencies resolve

For each constructor parameter, Diana looks up a provider by exact type (generic type arguments included — CrudRepository<Todo> only matches a provider bound to CrudRepository<Todo>). Matching happens in two tiers:

  1. Strong bindings — the provider's own class, plus the type named by

as: if given.

  1. Auto-binding candidates — every supertype the provider implements or

extends (transitively, excluding dart:* types).

Strong bindings win over candidates. Within a tier:

  • exactly one match → resolved;
  • more than one match → build error listing every candidate and where each

is declared;

  • none → missing provider build error naming the parameter and class that

needed it.

Interface auto-binding

If exactly one provider implements an interface, depending on the interface just works:

abstract interface class TodoRepository { ... }

@Repository()
class InMemoryTodoRepository implements TodoRepository { ... }

@Service()
class TodoService {
  TodoService(this.repo);        // gets InMemoryTodoRepository
  final TodoRepository repo;
}

Choosing among several implementations

When two classes implement the same interface, disambiguate with either:

as: — declare one of them the binding for that type:

@Repository(as: TodoRepository)
class PostgresTodoRepository implements TodoRepository { ... }

@Repository()                    // still injectable by its own type
class InMemoryTodoRepository implements TodoRepository { ... }

The as: type must actually be implemented/extended by the class, and two providers must not claim the same type with as:.

Qualifiers — name the providers and select by name at the injection point:

@Component(name: 'smtp')
class SmtpSender implements MailSender { ... }

@Component(name: 'log')
class LogSender implements MailSender { ... }

@Service()
class Notifier {
  Notifier(@Named('smtp') this.sender);
  final MailSender sender;
}

A qualified provider is only visible through @Named — it does not participate in unqualified resolution.

Scopes

enum Scope { singleton, request, transient }
Scope Lifetime Generated as
singleton (default) one instance for the application late final field on DianaContext
request one instance per HTTP request late final field on DianaRequestScope
transient new instance per injection point factory method (createX())

Rules, enforced at build time:

  • Nothing reachable from a singleton may be request-scoped (a singleton

outlives every request). A controller that depends on request-scoped providers must itself be request-scoped: @RestController('/x', Scope.request).

  • A transient that (transitively) depends on a request-scoped provider is

itself treated as request-bound.

  • Middleware must be singletons.

Note that a transient is created once per injection point: a singleton that receives a transient keeps that one instance. Transients shine when injected into request-scoped providers or when you call the generated factory yourself.

Injecting configuration values

@Value parameters are resolved from configuration, not from the graph:

@Service()
class Greeter {
  Greeter(@Value('app.greeting', defaultValue: 'hello') this.greeting);
  final String greeting;
}

What gets generated

For this graph:

@Repository()
class InMemoryTodoRepository implements TodoRepository {}

@Service()
class TodoService {
  TodoService(this.repo);
  final TodoRepository repo;
}

the generator emits (simplified — real output uses import prefixes):

class DianaContext {
  DianaContext(this.config);
  final DianaConfig config;

  late final InMemoryTodoRepository inMemoryTodoRepository =
      InMemoryTodoRepository();

  late final TodoService todoService = TodoService(inMemoryTodoRepository);
}

Fields appear in topological (dependency) order; late final makes construction lazy while the build-time cycle check guarantees safety. Deterministic output: rebuilding unchanged sources is byte-identical.

You can construct the graph yourself in tests with the generated buildDianaContext({DianaConfig? config}) — see Testing.

Errors you might see

Every failure mode has a dedicated diagnostic — duplicates, ambiguity, missing providers, cycles (with the full path printed), scope violations. They are all collected and reported together in a single build failure. See the build diagnostics reference.

Current limitations

  • Providers must be non-generic classes (generic dependencies like

CrudRepository<Todo> are fine — matched structurally).

  • All providers must live in the same package as the @DianaApplication

(cross-package component scanning is on the roadmap).

  • Named constructors and factory constructors are not used for injection.

Controllers and routing

Controllers are classes annotated with @RestController whose public instance methods declare routes with HTTP-method annotations. The generator turns each route method into an adapter that binds parameters, validates bodies, invokes your method and serializes the result — your controller code stays plain Dart.

import 'package:diana/diana.dart';

part 'todo_controller.diana.dart';   // required: adapters generate here

@RestController('/todos')
class TodoController {
  final TodoService service;
  TodoController(this.service);      // constructor injection

  @Get()
  List<TodoDto> list(@QueryParam('limit', '20') int limit) =>
      service.list(limit);

  @Get('/:id')
  TodoDto getById(@PathParam() int id) => service.getOrThrow(id);

  @Post()
  @ResponseStatus(201)
  TodoDto create(@Body() CreateTodoRequest body) => service.create(body);

  @Delete('/:id')
  void remove(@PathParam() int id) => service.delete(id);
}

Declaring routes

  • @RestController([path = '/', scope = Scope.singleton]) — mounts all

routes under path. Controllers join the DI graph; see scopes for request-scoped controllers.

  • @Get, @Post, @Put, @Delete, @Patch — each takes an optional

path relative to the controller: @Get('/:id'). Empty means the controller path itself.

  • Paths use :name segments for path parameters (/todos/:id). Routing is

a trie — matching is exact-segment based and fast; route registration order never affects matching.

  • Base and route paths are joined and normalized: '/todos' + '/:id' →

/todos/:id; trailing slashes are dropped.

  • For methods without a shorthand (HEAD, OPTIONS), use the base annotation:

@HttpRoute('HEAD', '/status').

  • Route methods must be public instance methods.
  • A request to an existing path with an unregistered method returns

405 Method Not Allowed; an unknown path returns the JSON 404.

Parameter binding

Every route-method parameter needs exactly one binding annotation — or be of type DianaRequest for raw access:

Annotation Source Notes
@PathParam([name]) :name path segment Must be non-nullable — the segment always exists when the route matches.
@QueryParam([name, defaultValue]) query string Nullable type ⇒ optional. defaultValue is written as a string and converted like the real value.
@Header([name]) request header Case-insensitive. Nullable type ⇒ optional.
@Body() JSON request body See bodies.
(none — DianaRequest type) the raw request Full access: headers, attributes, body.

name always defaults to the Dart parameter name.

Supported types for path/query/header: String, int, double, bool, num — plus their nullable forms for query/header. bool accepts true/1/false/0 (case-insensitive).

Conversion failures are automatic 400s with precise messages:

GET /todos/abc
→ 400 {"error":"bad_request","message":"Path parameter 'id' must be int, got 'abc'."}

A missing required (non-nullable, no default) query parameter or header is also a 400.

Request bodies

@Body() accepts these parameter types:

Type Behaviour
Map<String, dynamic> Raw decoded JSON object.
A DTO class Dto.fromJson(decodedMap); the class must expose factory Dto.fromJson(Map<String, dynamic>) (checked at build time).
List<Dto> JSON array, each element through fromJson.
List<String> / List<int> / … / List<dynamic> JSON array of primitives, .cast<T>().

Body handling is strict and automatic:

  • Content type other than application/json (or …+json) → 415.

A missing content type is tolerated.

  • Empty or malformed JSON, or the wrong JSON shape (array where an object

is expected, and vice versa) → 400.

  • If the DTO carries validation constraints, the generated

validator runs before your method — an invalid payload never reaches you (structured 400).

Return types

Declared return type Response
a DTO with toJson() 200, application/json, result.toJson()
List<Dto> 200, JSON array of toJson()
Map<String, dynamic> (and other JSON primitives/collections) 200, JSON
String 200, text/plain
void 204 No Content
DianaResponse passed through unchanged (full control)
Stream<ServerSentEvent> / Stream<Dto> 200, text/event-stream — see Server-Sent Events
Future<...> of any of the above awaited, then as above
  • @ResponseStatus(code) overrides the success status (201 for a POST,

etc.). It applies to JSON/text/void returns; a returned DianaResponse keeps its own status.

  • A nullable DTO return (TodoDto?) serializes null as a JSON null

body with the success status.

  • Returning a type with neither toJson() nor JSON-primitive shape is a

build error that tells you what to add.

  • Bodies and responses default to JSON; routes opt into other formats

(XML, custom codecs) with @Consumes/@Produces — see Content negotiation.

Errors thrown from handlers

Anything thrown inside a route (or the services it calls) flows through the exception pipeline — built-in HttpExceptions map to their status, @ControllerAdvice handlers map domain exceptions, everything else becomes an opaque 500. See Error handling.

  • Types referenced in route signatures must be imported **without an import

Middleware

Middleware intercept requests around handlers — logging, auth, headers, rate limiting. Diana's model is a class implementing one interface:

abstract interface class Middleware {
  FutureOr<DianaResponse> handle(DianaRequest request, Next next);
}

typedef Next = FutureOr<DianaResponse> Function(DianaRequest request);

Call next(request) to continue the chain; return a response directly to short-circuit (the handler never runs). You can act before next (inspect/annotate the request), after it (transform the response), or both.

@GlobalMiddleware(order: 0)
class TimingMiddleware implements Middleware {
  @override
  Future<DianaResponse> handle(DianaRequest request, Next next) async {
    final watch = Stopwatch()..start();
    final response = await next(request);
    return response.copyWith(headers: {
      ...response.headers,
      'x-response-time-ms': '${watch.elapsedMilliseconds}',
    });
  }
}

Registering middleware

Globally — annotate the class with @GlobalMiddleware:

@GlobalMiddleware(order: 0)
class LoggingMiddleware implements Middleware { ... }

Applies to every route. Lower order runs first (i.e. outermost); ties are broken by class name for deterministic builds. @GlobalMiddleware classes are automatically injectable singletons.

Per controller or per route — annotate the middleware class as a regular component and reference it with @UseMiddleware:

@Component()
class ApiKeyMiddleware implements Middleware {
  ApiKeyMiddleware(@Value('app.apiKey') this.expected);
  final String expected;

  @override
  Future<DianaResponse> handle(DianaRequest request, Next next) async {
    if (request.header('x-api-key') != expected) {
      return DianaResponse.json({'error': 'unauthorized'}, statusCode: 401);
    }
    return await next(request);
  }
}

@RestController('/admin')
@UseMiddleware([AuditMiddleware])          // every route in the controller
class AdminController {
  @Delete('/:id')
  @UseMiddleware([ApiKeyMiddleware])       // this route only
  void remove(@PathParam() int id) { ... }
}

@UseMiddleware takes an ordered list of types; each must be an injectable class implementing Middleware (verified at build time, with a clear error otherwise).

Execution order

For any request the chain is always:

global (sorted by order) → controller-level (listed order) → route-level (listed order) → handler

The first middleware sees the request first and the response last (onion model). Short-circuiting anywhere skips everything further in.

Middleware and DI

Middleware are ordinary providers: constructor injection, @Value configuration, interface auto-binding — everything from the DI guide applies. One restriction: **middleware must be singletons** (a request-scoped middleware is a build error).

Passing data to handlers

Use DianaRequest.attributes, a per-request Map<String, Object?> bag:

// middleware
request.attributes['userId'] = token.subject;
return next(request);

// handler (raw request access)
@Get('/me')
Map<String, dynamic> me(DianaRequest req) =>
    {'userId': req.attributes['userId']};

Errors thrown in middleware

The exception boundary wraps the whole chain: an HttpException or an advice-mapped exception thrown from middleware produces the same JSON error responses as one thrown from a handler. See Error handling.

Configuration

Diana loads configuration from a YAML file and lets any value be overridden through environment variables — the standard pattern for containerized deployments. Configuration is injected at startup: a missing required key fails the boot, not the first request.

Sources and precedence

  1. Environment variables (highest)
  2. The YAML file named by @DianaApplication(configFile: ...) —

default application.yaml, resolved against the working directory

A missing YAML file is fine: the app runs on environment variables and defaults alone.

The YAML file

server:
  host: 0.0.0.0
  port: 8080

app:
  apiKey: secret
  info:
    name: todo_api
    version: 1.0.0

Nested maps flatten to dot-separated keys: server.port, app.info.name. Lists are kept as opaque values (scalar coercion only — list-typed access is on the roadmap).

Environment overrides

Every key maps to an environment variable: **upper-case, dots and dashes become underscores**.

Key Variable

app.api-key APP_API_KEY

@Value — inject one key

Put @Value on a constructor parameter of any injectable class:

@Service()
class Greeter {

}

(build error otherwise).

  • Without a default, the key is required — missing means the app fails

@ConfigurationProperties — bind a section

Bind a whole configuration section to a typed class. The library needs a part directive (a binder function is generated):

import 'package:diana/diana.dart';

@ConfigurationProperties('app.mail')
class MailProps {
  final String host;      // ← app.mail.host (required)
  final int port;         // ← app.mail.port (required)
  final String? replyTo;  // ← app.mail.replyTo (optional)

  const MailProps({required this.host, required this.port, this.replyTo});
}

Rules:

  • Every constructor parameter binds from <prefix>.<paramName>.
  • Parameter types: String, int, double, bool, num — nullable

makes the key optional (bound to null when absent).

  • The class becomes an injectable singleton; depend on it anywhere:
@Service()
class Mailer {

}

Validation

Diana validates request DTOs declaratively: constraint annotations on fields become a generated validator that runs before your handler. An invalid body never reaches your code — the client gets a structured 400.

Declaring constraints

Annotate the fields of any class used with @Body(). The library needs a part directive (the validator is generated into it):

import 'package:diana/diana.dart';

part 'signup_request.diana.dart';

class SignupRequest {
  @NotBlank(message: 'name is required')
  @Size(min: 2, max: 50)
  final String name;

  @Email()
  final String email;

  @Min(18)
  @Max(130)
  final int? age;            // optional: constraints skip null

  @Pattern(r'^[a-z0-9_]+$', message: 'lowercase letters, digits and _ only')
  final String handle;

  @Valid()
  final Address? address;    // cascade into a nested DTO

  // constructor + fromJson/toJson ...
}

The constraint catalogue

Annotation Applies to Fails when
@NotNull({message}) any field value is null
@NotEmpty({message}) String, List, Set, Map empty
@NotBlank({message}) String empty or whitespace-only
@Min(value, {message}) numeric < value
@Max(value, {message}) numeric > value
@Size({min, max, message}) String, List, Set, Map length outside [min, max]
@Pattern(regex, {message}) String doesn't match the regex (full or partial per your regex anchors)
@Email({message}) String not shaped like an email address
@Valid() a DTO field, or List of DTOs delegates to the nested type's validator

Every constraint takes an optional message that replaces the default. Applying a constraint to an incompatible field type (@Min on a String) is a build error.

Null semantics

All constraints except @NotNull skip null values. Express requiredness with a non-nullable Dart type (enforced by your fromJson) or with @NotNull. This matches Jakarta Bean Validation semantics: @Min(1) int? priority means "if present, at least 1".

Cascading with @Valid

@Valid descends into a nested DTO (or each element of a List of DTOs). Nested field errors are prefixed with the path:

address.street        → from @Valid() final Address? address;
items[2].quantity     → from @Valid() final List<OrderItem> items;

The nested type must itself carry constraint annotations — @Valid into an unconstrained class is a build error.

The error response

A failed validation throws ValidationException, which the pipeline maps to:

HTTP 400
{
  "error": "validation_failed",
  "fields": {
    "name": ["name is required", "size must be between 2 and 50"],
    "email": ["must be a valid email address"]
  }
}

Messages per field appear in declaration order.

What gets generated

For each constrained class, a public $XValidator in the part file:

class $SignupRequestValidator implements Validator<SignupRequest> {
  const $SignupRequestValidator();

  @override
  ValidationResult validate(SignupRequest value) {
    final errors = <FieldError>[];
    checkNotBlank(value.name, 'name', errors, message: 'name is required');
    checkSize(value.name, 'name', errors, min: 2, max: 50);
    checkEmail(value.email, 'email', errors);
    ...
    return ValidationResult(errors);
  }
}

Generated code is one line per constraint; the semantics live in tested runtime helpers (checkNotBlank, checkMin, …). Route adapters invoke the validator automatically after fromJson; for List<Dto> bodies each element is validated.

Validating manually

Validators are ordinary classes — use them anywhere:

final result = const $SignupRequestValidator().validate(request);
if (!result.isValid) { ... }        // inspect result.errors
result.throwIfInvalid();            // or throw the standard 400

Default messages: must not be null, must not be empty, must not be blank, must be at least X, must be at most X, size must be between X and Y / at least X / at most X, must match pattern R, must be a valid email address.

The runtime types (Validator, ValidationResult, FieldError, ValidationException, the check* helpers) are documented in the runtime reference.

Error handling

Every request runs inside Diana's exception boundary. Whatever is thrown — from a handler, a service or middleware — is turned into a JSON error response through a fixed pipeline. Internals never leak: an unrecognized exception is an opaque 500.

The pipeline

When something is thrown, the first match wins:

  1. ValidationException → 400 with the

structured field map.

  1. @ControllerAdvice handlers (your generated advice chain) — checked

by exception type, most specific subtype first.

  1. HttpException (Diana's hierarchy) → its status code:

{"error": <reason>, "message": <message>}.

  1. Anything else → 500 {"error": "internal_server_error"}; the actual

error and stack trace go to the server's onUnhandled callback (default: printed), never to the client.

Built-in HTTP exceptions

Throw these anywhere for an immediate, correctly-shaped error response:

Exception Status error field
BadRequestException(message) 400 bad_request
UnauthorizedException([message]) 401 unauthorized
ForbiddenException([message]) 403 forbidden
NotFoundException([message]) 404 not_found
ConflictException(message) 409 conflict
UnsupportedMediaTypeException(message) 415 unsupported_media_type
UnprocessableEntityException(message) 422 unprocessable_entity
InternalServerErrorException([message]) 500 internal_server_error
HttpException(status, message, {reason}) any custom 
TodoDto getOrThrow(int id) =>
    repo.find(id) ?? (throw NotFoundException('No todo with id $id.'));
HTTP 404
{"error": "not_found", "message": "No todo with id 42."}

Parameter-binding and body-decoding failures throw these internally, which is why a bad :id is automatically a 400 and a non-JSON body a 415.

@ControllerAdvice — mapping domain exceptions

Domain code often shouldn't know about HTTP. Keep domain exceptions pure and map them in one place:

// domain
class BookNotFound implements Exception {
  final int id;
  const BookNotFound(this.id);
}

// web layer
@ControllerAdvice()
class ErrorAdvice {
  @ExceptionHandler(BookNotFound)
  DianaResponse onBookNotFound(BookNotFound e, DianaRequest req) =>
      DianaResponse.json(
        {'error': 'book_not_found', 'id': e.id, 'path': req.path},
        statusCode: 404,
      );
}

Rules (checked at build time):

  • @ControllerAdvice classes are injectable singletons — constructor

injection works. They must declare at least one handler.

  • Handler signature: (E exception) or `(E exception, DianaRequest

request), where E is exactly the type named in @ExceptionHandler(E)`.

  • Return type: DianaResponse or Future<DianaResponse>.
  • A handler also catches subtypes of its exception type. When several

handlers match, the most specific type wins (a DerivedError handler beats a BaseError handler regardless of declaration order); exact ties fall back to declaration order.

  • Advice handlers apply globally — to every route, and to middleware too.

You may register multiple advice classes; their handlers merge into one chain.

Customizing unhandled-error logging

The generated buildDianaServer() wires the advice chain automatically. The onUnhandled hook belongs to DianaServer; today it defaults to printing to stdout. Constructing a DianaServer manually (advanced) lets you replace it — see the runtime reference.

WebSockets

Diana's WebSocket support mirrors Spring's WebSocketHandler / WebSocketSession model: implement a handler interface, annotate it with a path, and the framework wires the HTTP upgrade, the lifecycle callbacks and dependency injection.

import 'package:diana/diana.dart';

@WebSocketController('/ws/echo')
class EchoHandler extends BaseWebSocketHandler {
  @override
  void onOpen(WebSocketSession session) => session.sendText('welcome');

  @override
  void onMessage(WebSocketSession session, WebSocketMessage message) {
    if (message is TextMessage) session.sendText(message.text);
  }
}

Clients connect with any WebSocket client:

final socket = await WebSocket.connect('ws://localhost:8080/ws/echo');

The handler lifecycle

WebSocketHandler declares four callbacks (Spring's afterConnectionEstablished / handleMessage / handleTransportError / afterConnectionClosed, with shorter names). Extend BaseWebSocketHandler to override only what you need; all callbacks may be async.

Callback When
onOpen(session) Connection established.
onMessage(session, message) A frame arrived — TextMessage(text) or BinaryMessage(data) (pattern-match the sealed type).
onError(session, error, stackTrace) A transport error or an exception escaped a callback; the connection is closed with code 1011 afterwards.
onClose(session, code, reason) Connection closed by either side; always called last.

Messages within one connection are dispatched sequentially — awaiting in onMessage back-pressures that connection's frames.

The session

WebSocketSession is your channel to one connected peer:

Member Description
id Unique per connection (ws-1, ws-2, …).
uri The URI the client connected to.
pathParameters Route parameters — @WebSocketController('/ws/chat/:room') ⇒ session.pathParameters['room'].
queryParameters Handshake query string.
attributes Per-connection Map<String, Object?> bag, alive for the whole session.
isOpen Whether the connection is (believed) open.
sendText(text) / sendBytes(data) Send a frame; return false instead of throwing when already closed.
close([code, reason]) Close the connection (code: 1000 or 3000–4999).

Keep a Set<WebSocketSession> in your handler to broadcast — see the chat example.

Handler instances and scope

@WebSocketController(path, [scope]) — the class joins the DI graph (constructor injection, @Value, everything from the DI guide applies):

  • Scope.singleton (default): one shared handler for all connections —

Spring's default. Keep per-connection state in session.attributes, and connection registries as handler fields.

  • Scope.transient: a fresh handler per connection — instance

fields become per-connection state, no bookkeeping needed.

  • Scope.request doesn't apply to WebSockets and is a build error.
@WebSocketController('/ws/game', Scope.transient)
class GameSession extends BaseWebSocketHandler {
  GameSession(this.engine);        // injected per connection
  final GameEngine engine;
  int score = 0;                   // this connection's state
}

Handshake interceptors

@UseMiddleware on a @WebSocketController runs the listed middleware on the handshake request:

@WebSocketController('/ws/chat/:room')
@UseMiddleware([ApiKeyMiddleware])
class ChatHandler extends BaseWebSocketHandler {
  @override
  void onOpen(WebSocketSession session) {
    final user = session.attributes['user'];   // set by the middleware
    ...
  }
}
  • A middleware that short-circuits (e.g. returns a 401) **blocks the

upgrade** with that response.

  • request.attributes set during the handshake are copied into

session.attributes.

  • Exceptions in handshake middleware go through the normal exception

pipeline (advice, HttpException mapping).

  • Global middleware do not apply to handshakes — interceptors are

explicit opt-in (mirroring Spring's HandshakeInterceptor registration).

What does not apply

  • After the upgrade, middleware and @ControllerAdvice play no role in

socket traffic; errors reach the handler's onError.

  • The validation machinery targets request bodies; decode

and validate WebSocket payloads yourself (e.g. $MyDtoFromJson(jsonDecode(message.text)) plus a generated $MyDtoValidator).

Build-time checks

  • The annotated class must implement WebSocketHandler (or extend

BaseWebSocketHandler).

  • Endpoint paths must be unique across the application.
  • Scope.request is rejected.

See build diagnostics.

Application lifecycle

Diana applications have an explicit lifecycle:

buildDianaApp() → initialize() → serve() → [SIGINT/SIGTERM] → close() → dispose()

runDiana() drives all of it (via DianaRuntime.run); tests and embeddings can drive each step themselves.

@PostConstruct / @PreDestroy

Run code after construction and during shutdown, Spring-style:

@Repository()
class Db {
  late final Connection _conn;

  @PostConstruct()
  Future<void> connect() async => _conn = await Connection.open(...);

  @PreDestroy()
  Future<void> disconnect() => _conn.close();
}

Rules (build-verified): public instance method, no parameters, returns void or Future<void>, at most one of each per class, **singleton providers only**.

  • initialize() constructs every singleton in dependency order and awaits

each @PostConstruct — including @ConfigurationProperties binding, so missing required config keys fail here, before the port opens.

  • dispose() runs @PreDestroy hooks in reverse dependency order,

after the server has stopped and in-flight requests have drained.

Publishing application events from @PostConstruct is fully supported — listeners are registered before initialization runs.

Graceful shutdown

runDiana() installs SIGINT/SIGTERM handlers (SIGTERM skipped on Windows). On a signal it stops accepting connections, waits for in-flight requests, then disposes. Programmatic control:

final shutdown = Completer<void>();
await DianaRuntime.run(
  () async { final app = await buildDianaApp(); ... },
  installSignalHandlers: false,
  shutdownTrigger: shutdown.future,
);

The generated DianaApp

final app = await buildDianaApp(config: ..., overrides: ...);
app.context;         // the DI container
app.server;          // the DianaServer
await app.initialize();
await app.server.serve(port: 0);
...
await app.server.close();
await app.dispose();

When @Scheduled tasks exist, app.initialize() also starts the scheduler and app.dispose() stops it (see Observability § Scheduling).

Test overrides — DianaOverrides

Every provider gets a nullable slot in the generated DianaOverrides class; a non-null value replaces the real provider **everywhere it is injected** (Spring @MockBean analog):

class FakeRepo implements InMemoryTodoRepository { ... }

  overrides: DianaOverrides(inMemoryTodoRepository: FakeRepo()),
);
expect(ctx.todoService.repo, isA<FakeRepo>());

Notes:

  • Overrides are per concrete provider class (unambiguous when several

classes implement one interface). Fakes can implements the concrete class.

  • Works with buildDianaContext, buildDianaServer, buildDianaApp and

runDiana.

  • Overriding a transient provider effectively makes it a singleton for that

context — exactly what tests want.

  • With multi-isolate serving, overrides must be sendable (tests normally

run single-isolate; not a practical concern).

Application events

Diana's analog of Spring's ApplicationEventPublisher: publish plain Dart objects as events, and any singleton provider can react to them by annotating a method with @EventListener. Listener wiring is resolved at compile time — the generated context registers every listener before your application initializes.

Declaring a listener

Any singleton provider (service, component, controller, middleware, …) can listen. The method takes exactly one parameter — the event type — and returns void or Future<void>:

class TodoCreated {
  final int id;
  final String title;
  const TodoCreated(this.id, this.title);
}

@Component()
class TodoAuditListener {
  @EventListener()
  void onTodoCreated(TodoCreated event) => log(event.title);
}

Matching is by type, subtypes included (Spring semantics): a listener on OrderEvent also receives OrderCreated extends OrderEvent. Request-scoped and transient providers cannot listen (build error) — a listener must have a stable instance for the application's lifetime.

Publishing

Inject DianaEventPublisher (the interface, not the bus) into any provider:

@Service()
class TodoService {
  final DianaEventPublisher publisher;
  TodoService(this.publisher);

  Future<TodoDto> create(CreateTodoRequest request) async {
    final todo = repo.save(request.title);
    await publisher.publish(TodoCreated(todo.id, todo.title));
    return todo;
  }
}

publish is synchronous in the Spring sense: it runs every matching listener — in registration order, awaiting each one — before it returns, so events participate in the request flow. A listener throwing propagates to the publisher and skips the remaining listeners; an uncaught error therefore surfaces exactly like any other exception in the calling route (exception pipeline, @ControllerAdvice, …).

Registration order is deterministic: providers in dependency (topological) order, methods in declaration order within a class.

publish vs broadcast

Local listeners Other isolates
publish(event) awaited, errors propagate not delivered
broadcast(event) awaited, errors propagate delivered fire-and-forget

With a single isolate (the default), broadcast behaves exactly like publish. With server.isolates > 1, broadcast also relays the event to every other isolate over the runtime's control plane; each isolate's listeners then run against their own providers. This is the built-in answer to multi-isolate coordination — see operations.

Cross-isolate rules:

  • Events must be plain data. The event object crosses the isolate

boundary as-is; anything holding a ReceivePort, socket or other native resource fails fast with ArgumentError: Diana broadcast failed: event of type X is not sendable across isolates. … — before any local listener runs.

  • Remote delivery is fire-and-forget: the publisher never observes

remote listener errors (they go to the bus's onError, which logs by default), and there is no cross-isolate ordering guarantee.

  • Delivery is exactly-once per isolate (hub-and-spoke relay through the

main isolate; no loops).

  • During a worker's own initialize() the bridge is not wired yet, so a

broadcast from startup code delivers locally only.

Lifecycle timing

Listeners are registered in the generated DianaContext constructor, before initialize() runs — so publishing from a @PostConstruct hook is fully supported and delivered. Publishing from a provider constructor is discouraged: providers are late final, and an event fired mid-graph construction can force a circular initialization (LateInitializationError). Move that publish to @PostConstruct.

Registration itself is lazy: a listener provider is only constructed when the first matching event fires (or when initialize() builds it, whichever comes first).

Testing

The bus is plain Dart — no server needed:

await ctx.eventBus.publish(const TodoCreated(1, 'unit test'));
expect(ctx.todoAuditListener.seen, ['unit test']);

Or construct a DianaEventBus directly in unit tests and register handlers with bus.on<MyEvent>(...). For publisher-side tests, inject a fake DianaEventPublisher through DianaOverrides as usual.

CORS and static files

CORS

Two ways to enable it; both include automatic OPTIONS preflight routes.

Globally, from configuration:

server:
  cors:
    enabled: true
    allowedOrigins: ["https://app.example"]   # default ['*']
    # allowedMethods: [GET, POST]             # default: methods on the path
    allowedHeaders: ["*"]                     # '*' echoes the preflight
    exposedHeaders: []
    allowCredentials: false
    maxAge: 3600                              # preflight cache, seconds

Per controller or route, with @CrossOrigin (same fields, camelCase):

@RestController('/info')
@CrossOrigin(origins: ['https://dashboard.example'])
class InfoController { ... }

Semantics:

  • Route annotation replaces controller annotation replaces global

config — whole-policy replacement, no field merging.

  • @CrossOrigin enables CORS on its routes even when the global config is

disabled.

  • Disallowed origins simply get no CORS headers (the browser blocks); a

valid preflight answers 204 with Access-Control-Allow-* headers and Vary: Origin.

  • With allowCredentials: true, a * origin list echoes the caller's

origin (the spec forbids literal * with credentials).

  • Registering your own OPTIONS route on a path suppresses the automatic

preflight for it.

Static files

Serve a directory through the engine's hardened static handler (ETag, Range/conditional requests, path-traversal protection):

server:
  static:
    enabled: true
    dir: public          # filesystem directory
    prefix: /static      # URL prefix
    index: index.html    # served on directory hits
    spa: false           # true: serve index on ANY miss under the prefix
    cacheMaxAge: 3600    # Cache-Control max-age, seconds
  • GET /static/… and HEAD are served from dir; anything outside the

prefix is untouched, so API routes coexist.

  • spa: true turns misses under the prefix into index.html — client-side

routers (Flutter web, React) work unhydrated.

  • Purely a runtime feature — no annotations, no codegen; DianaServer

mounts it during serve() when enabled.

Content negotiation

By default every Diana route speaks JSON. Content negotiation lets a route accept and produce other formats — XML out of the box, anything else via a pluggable codec — without changing your DTOs or the validation pipeline. Three pieces work together:

  1. A BodyCodec translates between a wire format and the intermediate

representation the DTO codecs already consume (Map/List/scalars).

  1. @Consumes restricts which request content types a route accepts.
  2. @Produces lists the response formats a route can produce; the

first one the request's Accept header allows wins.

Registering a codec

A codec is an ordinary injectable: annotate a singleton class implementing BodyCodec and the generator wires it into the server. To enable the built-in XML codec, subclass it:

import 'package:diana/diana.dart';

@Component()
class AppXmlCodec extends XmlCodec {}

That's all — every route annotated with application/xml can now speak XML. JSON is always registered (it also accepts …+json content types like application/hal+json).

Custom formats implement the interface directly:

@Component()
class CsvCodec implements BodyCodec {
  @override
  List<String> get mimeTypes => ['text/csv'];   // first entry = canonical

  @override
  Object? decode(String body) { /* → Map/List/scalars; FormatException on bad input */ }

  @override
  String encode(Object? value) { /* Map/List/scalars → wire format */ }
}

Codecs must be singletons — a request-scoped codec is a build error. The decoded value feeds the same pipeline as JSON: DTO fromJson, validation, everything applies unchanged.

@Consumes — request side

@Post('/xml')
@Consumes(['application/xml'])
TodoDto create(@Body() CreateTodoRequest body) => service.create(body);
  • The request's Content-Type must match one of the listed types, and a

codec for it must be registered — otherwise **415 Unsupported Media Type**. Malformed bodies (or the wrong shape, e.g. an array where an object is expected) are 400.

  • The annotated set replaces the default — @Consumes(['application/xml'])

no longer accepts JSON; list both if you want both.

  • Method-level replaces controller-level entirely (same precedence rule as

@CrossOrigin).

  • Requires a codec-decoded @Body parameter (Map, List or DTO).

String, FormData and raw-request bodies bypass codecs, so combining them with @Consumes is a build error.

@Produces — response side

@Post('/xml')
@Consumes(['application/xml'])
@Produces(['application/xml', 'application/json'])
TodoDto create(@Body() CreateTodoRequest body) => service.create(body);
  • The response is encoded with the first listed type the request's

Accept header allows — server preference order, like Spring. No Accept header accepts everything.

  • Nothing acceptable → 406 Not Acceptable.
  • Applies to JSON-encodable returns (DTO, List of DTOs, Map, List).

String, void and DianaResponse returns are not negotiated (build error), and Stream returns always produce text/event-stream (see Server-Sent Events).

Both annotations are projected into the generated OpenAPI document: requestBody.content and response content list the declared MIME types.

The XML convention

XML has no native notion of objects, arrays or types, so XmlCodec maps it to Map/List/scalars with a fixed convention:

Decoding (application/xml, text/xml):

  • The root element's name is ignored; its children become map keys.
  • Repeated sibling elements become a List.
  • An element whose children are all <item> becomes a List.
  • Leaf text is inferred in order: int → double → bool → String.
  • An empty element decodes to null.
  • Attributes are ignored (documented limitation).

Encoding: the root element is <response>; list entries are emitted as repeated elements (or <item> at the top level).

<todo>                          <!-- root name ignored -->
  <title>learn diana</title>    <!-- {'title': 'learn diana', -->
  <priority>2</priority>        <!--  'priority': 2 (int inferred), -->
  <done>false</done>            <!--  'done': false} -->
</todo>

One asymmetry to know: a decoded list with a single element is indistinguishable from a scalar, so it decodes as a scalar. If a DTO field needs List<T> semantics for single values, prefer JSON for that route or model the field as accepting both.

Scalar inference is what makes typed DTO fields work: fromJson casts the inferred values, and a mismatch surfaces as a 400 through the normal DTO decoding path.

Manual negotiation

The generated adapters call two public helpers you can also use directly in a route returning DianaResponse:

final map = await decodeMapBody(req, consumes: ['application/xml']);     // 415/400
return negotiatedResponse(req, payload, produces: ['application/xml']);  // 406

decodeListBody is the array-shaped sibling. The registry itself travels on the request as req.codecs (BodyCodecRegistry.forMime).

Server-Sent Events

Server-Sent Events (SSE) push a stream of events over a single HTTP response — the browser's EventSource API consumes them natively. In Diana, a route becomes an SSE endpoint by returning a Stream. No annotation needed.

Two supported stream shapes

Stream<ServerSentEvent> — full control over the SSE fields:

@RestController('/events')
class EventsController {
  @Get('/ticks')
  Stream<ServerSentEvent> ticks() async* {
    for (var i = 1; i <= 3; i++) {
      yield ServerSentEvent('tick $i', id: '$i', event: 'tick');
      await Future<void>.delayed(const Duration(seconds: 1));
    }
  }
}

Stream<Dto> — any DTO with a toJson() (or @Json); each element is JSON-encoded as the event's data:

@Get('/todos')
Stream<TodoDto> todoFeed() => repository.changes();

Both may be wrapped in Future (Future<Stream<…>>). Any other element type is a build error, as is combining a Stream return with @ResponseStatus (SSE responses are always 200) or @Produces (always text/event-stream).

What Diana sends

  • Status 200, content-type: text/event-stream,

cache-control: no-cache.

  • Spec-compliant framing: id:, event:, retry: fields when set;

multi-line data is split into one data: line per line; events are separated by a blank line.

  • Immediate flushing: streamed responses bypass the buffered response

path and write chunked frames straight to the socket, so an event is on the wire the moment your stream emits it.

id: 1
event: tick
data: tick 1

Heartbeats and disconnects

Every server.sse.heartbeatSeconds (default 15, 0 disables) Diana interleaves an SSE comment line (: keep-alive) so proxies keep the connection open. The heartbeat doubles as a disconnect backstop: writing to a dead socket fails, which tears the response down.

When the client disconnects, your source stream's onCancel runs — use it to release resources:

@Get('/feed')
Stream<ServerSentEvent> feed() {
  final controller = StreamController<ServerSentEvent>();
  final timer = Timer.periodic(const Duration(seconds: 1),
      (t) => controller.add(ServerSentEvent('t=${t.tick}')));
  controller.onCancel = () => timer.cancel();   // runs on disconnect
  return controller.stream;
}

A finite stream ends the response normally when it completes.

ServerSentEvent

Field SSE line Meaning
data data: Payload (required; multi-line split per spec)
id id: Lets clients resume with Last-Event-ID
event event: Event type dispatched to addEventListener
retryMs retry: Client reconnection delay (ms)

ServerSentEvent.json(object) JSON-encodes the payload — it's what generated adapters use for Stream<Dto> routes.

Consuming

const es = new EventSource('/events/ticks');
es.addEventListener('tick', (e) => console.log(e.lastEventId, e.data));

Or with curl: curl -N http://localhost:8080/events/ticks.

Manual responses

For full control, return DianaResponse and build the stream yourself with the same public pieces the adapters use:

return sseResponse(req, events);                       // heartbeat from config
return DianaResponse.stream(encodeSse(events),          // fully manual
    mimeType: 'text/event-stream');

encodeSseEvent frames a single event if you need the raw text.

OpenAPI

SSE routes appear in the generated document with a 200 response of content type text/event-stream.

gRPC

Diana serves gRPC next to HTTP from the same dependency injection graph: annotate a class extending your protoc-generated service base with @GrpcService() and the generated DianaApp runs a gRPC server on its own port, integrated with the application lifecycle.

gRPC support lives in a separate package, diana_grpc — the only Diana package that depends on package:grpc. HTTP-only applications carry no gRPC dependency.

Setup

# pubspec.yaml
dependencies:
  diana: ^0.6.0
  diana_grpc: ^0.6.0
  grpc: ^4.0.0
  protobuf: ^4.0.0

Generate Dart code from your .proto (commit the output — it's source):

dart pub global activate protoc_plugin
protoc --dart_out=grpc:lib/src/generated -Iprotos protos/greeter.proto

Writing a service

Extend the generated XServiceBase and annotate it. The class is a regular singleton injectable — constructor injection, @Value, @PostConstruct, everything applies:

import 'package:diana/diana.dart';
import 'package:grpc/grpc.dart' show ServiceCall;

import '../src/generated/greeter.pbgrpc.dart';

@GrpcService()
class GreeterService extends GreeterServiceBase {
  final String greetingPrefix;

  GreeterService(
      @Value('app.greeting', defaultValue: 'Hello') this.greetingPrefix);

  @override
  Future<HelloReply> sayHello(ServiceCall call, HelloRequest request) async =>
      HelloReply()..message = '$greetingPrefix, ${request.name}!';
}

The class must extend a package:grpc Service (your protoc-generated base does) — anything else is a build error. @GrpcService cannot be combined with other role annotations (@Service, @RestController, …).

What the generator wires

With at least one @GrpcService class, the composition root gains a DianaGrpcServer holding every service, exposed as app.grpcServer:

  • initialize() starts gRPC after @PostConstruct hooks ran.
  • Graceful shutdown stops gRPC first (waiting for in-flight calls),

then HTTP.

  • app.grpcServer.port is the bound port (useful with grpc.port: 0 in

tests).

Without @GrpcService classes nothing is emitted and diana_grpc isn't referenced.

Configuration

Key Default Meaning
grpc.enabled true Serve gRPC (false skips serving; grpcServer stays null-op)
grpc.host 0.0.0.0 Bind address
grpc.port 9090 Port (0 for ephemeral in tests)

Standard HTTP keys are untouched — the servers are independent.

Limitations (v0.3)

  • Single isolate only: with server.isolates > 1, serve() fails

fast (gRPC serving supports a single isolate; set server.isolates to 1 or disable gRPC.). Socket sharing across isolates for gRPC is unverified.

  • Interceptors can be passed to a hand-constructed DianaGrpcServer but

are not yet discoverable through DI.

  • No TLS for the gRPC listener yet (put a proxy in front, or serve

HTTP-only behind the same proxy).

Authentication and authorization

Diana's Spring Security analog lives in the optional diana_auth package: pluggable authentication strategies, an injectable principal, and @Secured / @RolesAllowed guards the generator wires into your routes, WebSocket handshakes and gRPC services.

The design splits authentication (who are you?) from authorization (are you allowed?), exactly like Spring:

  • An AuthenticationMiddleware runs a chain of strategies and stamps

the authenticated principal onto the request. It never rejects anonymous requests — it only establishes identity.

  • Guards (@Secured, @RolesAllowed) enforce access at each route.

Setup

# pubspec.yaml
dependencies:
  diana: ^0.6.0
  diana_auth: ^0.6.0

Assembling the authentication filter

Subclass AuthenticationMiddleware, pick the strategies your app accepts, and register it — usually as a @GlobalMiddleware so it runs before every route:

import 'package:diana/diana.dart';
import 'package:diana_auth/diana_auth.dart';

@GlobalMiddleware(order: -100)
class AppAuth extends AuthenticationMiddleware {
  AppAuth(@Value('auth.jwt.secret') String secret)
      : super(authenticators: [
          JwtAuthenticator(Hs256TokenVerifier(secret)),
          ApiKeyAuthenticator(myKeyStore),
        ]);
}

Strategies run in order; the first one that recognizes credentials wins. A strategy returns null when the request carries no credentials **for its scheme** (the chain continues), or throws InvalidCredentialsException when credentials are present but invalid — an immediate 401 with a WWW-Authenticate challenge (a bad token is never silently downgraded to anonymous). A request with no credentials at all passes through anonymously; enforcement happens at the guards.

Built-in strategies

All produce an AuthPrincipal { String name; Set<String> roles; Map<String, Object?> attributes; } and implement the Authenticator interface, so you can add your own.

JWT (Authorization: Bearer <token>)

JwtAuthenticator(Hs256TokenVerifier(secret), rolesClaim: 'roles')

Hs256TokenVerifier validates HS256 signatures in-package (no heavyweight dependency) and is hardened: it accepts only alg: HS256 (rejecting none and algorithm-confusion), compares signatures in constant time, and enforces exp/nbf with a configurable clock skew plus optional iss/aud checks. sub becomes the principal name; the roles claim accepts a JSON list or a space-delimited string (covering OAuth scope).

TokenVerifier is an interface — plug RS256/JWKS from any external library by implementing it. To mint tokens (login endpoints, tests) use Hs256TokenSigner:

final token = Hs256TokenSigner(secret)
    .sign(Hs256TokenSigner.claimsFor('ada', roles: {'admin'}));

HTTP Basic

BasicAuthenticator(myUserStore, realm: 'api')

Provide a UserStore { Future<AuthPrincipal?> verify(String username, String password); }. The store owns password hashing — Diana never sees a hash.

API key

ApiKeyAuthenticator(myValidator, headerName: 'X-API-Key')

Provide an ApiKeyValidator { Future<AuthPrincipal?> validate(String key); }.

Authorizing routes

Annotate controllers or methods (method-level replaces controller-level, like @CrossOrigin):

@RestController('/admin')
@Secured()                              // every route requires auth
class AdminController {
  @Get('/stats')
  Stats stats() => ...;

  @Delete('/users/:id')
  @RolesAllowed(['admin'])              // ...and this one, the admin role
  void deleteUser(@PathParam() int id) => ...;
}
  • @Secured() → 401 for anonymous requests.
  • @RolesAllowed([...]) → 401 for anonymous, 403 when the principal

holds none of the listed roles (any-of semantics). It implies @Secured.

The generator appends the matching guard as the last middleware of the route, so it runs after your authentication filter and immediately before the handler. Fail-closed: with no authentication middleware present, every request is anonymous and secured routes return 401.

A security annotation placed where it would have no effect (a @Service, a non-route method) is a build error — a silently ignored guard is a hole you think is closed.

Reading the principal

Bind it with @Principal():

@Get('/me')
@Secured()
Profile me(@Principal() AuthPrincipal user) => Profile(user.name, user.roles);

A non-nullable parameter throws 401 when unauthenticated; a nullable one (AuthPrincipal?) receives null. In middleware or raw handlers, read request.attributes[principalAttributeKey] directly (the constant is exported from package:diana).

WebSockets

Authentication is applied at the handshake. Global middleware do not run on handshakes, so list the authentication middleware explicitly and add a guard:

@WebSocketController('/ws/chat/:room')
@UseMiddleware([AppAuth])   // authenticate the upgrade
@Secured()                  // reject anonymous upgrades with 401
class ChatHandler extends BaseWebSocketHandler {
  @override
  void onOpen(WebSocketSession session) {
    final principal = session.attributes[principalAttributeKey];
    // ...the authenticated principal is copied into the session.
  }
}

gRPC

gRPC services are secured the same way — @Secured / @RolesAllowed on the @GrpcService class. The generator discovers your AuthenticationMiddleware provider and installs a package:grpc interceptor that authorizes calls from their metadata (authorizeMetadata), returning UNAUTHENTICATED or PERMISSION_DENIED.

Limitations (v1): gRPC interceptors are server-wide, so every @GrpcService must declare identical security (a build error otherwise); principal injection into service methods is not yet available.

Persistence

Diana's data story lives in the optional diana_data package: an injectable query executor over the knexdart query builder, Spring-style @Transactional methods, opt-in migrations and a database health check.

It is driver-agnostic — diana_data depends only on knex_dart core; you pick the driver package (knex_dart_postgres, knex_dart_sqlite, …) and supply the connection through a small connector.

Setup

# pubspec.yaml
dependencies:
  diana: ^0.6.0
  diana_data: ^0.6.0
  knex_dart_sqlite: ^0.4.0   # your driver of choice

The connector

Write a DatabaseConnector subclass (a provider) that opens the driver connection and closes it. You own the driver import and the driver-specific close call — Diana never imports a driver:

import 'package:diana/diana.dart';
import 'package:diana_data/diana_data.dart';
import 'package:knex_dart_sqlite/knex_dart_sqlite.dart';

@Component()
class AppDb extends DatabaseConnector {
  @override
  Future<Object> connect(DianaConfig config) => KnexSQLite.connect(
        filename: config.get<String>('db.file'),
      );

  @override
  Future<void> close(Object connection) => (connection as KnexSQLite).close();
}

Diana opens the connection at the start of startup (before any provider, so a repository's @PostConstruct can already query) and closes it at the end of graceful shutdown. Declare exactly one connector — zero (while using the database) or many are build errors.

Repositories

Inject Database into any provider and use the knex query builder. Build a query with db.table('...') (and .where, .insert, .update, …), then execute it with db.select/insert/update/delete:

@Repository()
class PostRepository {
  final Database db;
  PostRepository(this.db);

  Future<List<Map<String, dynamic>>> all() => db.select(db.table('posts'));

  Future<void> add(String title) =>
      db.insert(db.table('posts').insert({'title': title}));

  Future<List<Map<String, dynamic>>> raw() => db.raw('SELECT 1');
}

Database.select/insert/… return List<Map<String, dynamic>> rows; map them to your DTOs in the repository.

Transactions

Annotate a service method with @Transactional and Diana runs it inside a database transaction — every write commits together or rolls back together:

@Service()
class BlogService {
  final PostRepository posts;
  BlogService(this.posts);

  @Transactional()
  Future<void> publishPair(String a, String b) async {
    await posts.add(a);
    await posts.add(b);   // if this throws, the first insert is undone
  }
}

How it works: the generator emits a proxy subclass ($Tx$BlogService) that overrides each @Transactional method to wrap the call in an ambient transaction. Repositories don't change — Database transparently routes queries to the current transaction (via a Zone) when one is active, and to the pooled connection otherwise.

  • Propagation is REQUIRED: a @Transactional method called from another

joins the enclosing transaction as a savepoint — the inner method can roll back independently while the outer commits.

  • Rollback on throw: an uncaught exception rolls the transaction (or

savepoint) back and rethrows, so it still flows through your @ControllerAdvice / exception pipeline.

Constraints (build errors): the class must be extendable (not final/base/sealed), the methods must return Future, and @Transactional only applies to @Service/@Component/@Repository providers.

Migrations

Set db.migrations.dir and Diana runs every *.sql file in that directory (lexically sorted) that hasn't been applied yet, once each, during startup — tracked in a _diana_migrations table. It is opt-in: with the key unset, nothing runs.

db:
  migrations:
    dir: migrations
-- migrations/001_create_posts.sql
CREATE TABLE posts (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  title TEXT NOT NULL
);

}

OpenAPI

Diana generates an OpenAPI 3.0 document at build time from the same single classification pass that generates your route adapters — the spec cannot drift from the actual routes.

Enabling

server:
  openapi:
    enabled: true          # default false
    title: Todo API        # patched into info.title
    version: 1.2.3         # patched into info.version

The document is embedded in the generated code as a deterministic constant and served at GET /openapi.json (guarded at runtime — toggling needs no rebuild). Point Swagger UI or any OpenAPI tool at it.

What's in the document

  • Paths and operations for every @RestController route

(/todos/:id → /todos/{id}), with operationId (Controller_method) and the controller name as tag.

  • Parameters from @PathParam/@QueryParam/@Header: location,

requiredness (nullable or defaulted ⇒ optional), primitive schema and default value.

  • Request bodies: $ref to the DTO schema for @Body() DTOs (arrays

for List<Dto>), text/plain for String bodies, multipart/form-data for FormData, unconstrained objects for raw Map/List bodies.

  • Responses keyed by the effective status (@ResponseStatus, 204 for

void) with the return schema.

  • Schemas (components/schemas) for every @Json class and every

validated DTO: property types (including DateTime → string/ date-time, enums with their values, nested $refs), required from non-nullable fields, and validation constraints mapped to minLength/maxLength/minimum/maximum/pattern/format: email (@NotBlank/@NotEmpty imply minLength: 1).

  • Content negotiation: @Consumes/@Produces MIME lists are

projected into requestBody.content and response content (same schema per MIME type); SSE routes (Stream returns) are documented as a 200 with text/event-stream content.

Best-effort areas (documented, not errors): DTOs that are neither @Json nor validated (e.g. plain json_serializable classes) appear as unconstrained {} schemas; DianaResponse returns have unspecified content.

Branding

info.title/info.version are patched at startup from server.openapi.title/server.openapi.version (via patchOpenApiInfo), keeping the build-time constant deterministic while letting deployments brand the spec.

class DbHealthIndicator implements HealthIndicator {

Scheduled tasks

@Scheduled runs a method on a fixed schedule, integrated with the application lifecycle: tasks start after initialize() (so @PostConstruct has run) and stop during dispose() (awaiting the in-flight run).

@Component()
class CleanupJob {
  @Scheduled(fixedRate: 60000)          // every 60s, tick-based
  Future<void> sweep() async { ... }

  @Scheduled(fixedDelay: 5000, initialDelay: 1000)
  void heartbeat() { ... }              // 5s after each completed run
}

Semantics:

  • Exactly one of fixedRate/fixedDelay (milliseconds; build error

otherwise). initialDelay delays the first run.

  • fixedRate skips a tick while the previous run is still in flight —

no unbounded queueing. fixedDelay re-arms after completion.

  • Method rules: public instance method, no parameters, void/Future<void>,

singleton provider (all build-verified).

  • Task errors are reported (stderr by default) and never stop the schedule.
  • No cron expressions yet.

With multi-isolate serving, remember tasks run once per isolate.

Operations: HTTPS, isolates, profiles

HTTPS

Configure certificate and key paths; the server switches to TLS:

server:
  ssl:
    certPath: certs/fullchain.pem
    keyPath: certs/privkey.pem
    # keyPassword: optional

Both paths are required together (startup error otherwise). The startup log switches to https://. Terminating TLS at a reverse proxy and serving plain HTTP behind it is equally supported — just omit server.ssl.*.

Multi-isolate serving (experimental)

server:
  isolates: 4

runDiana() (through DianaRuntime.run) spawns n - 1 worker isolates. Each worker runs the full bootstrap — its own DianaContext, its own initialize() — and binds the same port with shared sockets; the OS distributes connections. The main isolate owns the signal handlers and coordinates worker shutdown (workers close and dispose before the main isolate does).

Constraints:

  • Everything captured by the bootstrap must be sendable across isolates.

The generated bootstrap captures only DianaConfig (immutable primitives) and the overrides value — const DianaOverrides() is fine, live mock instances generally are not.

  • State is per isolate: in-memory repositories, caches and @Scheduled

tasks run once per isolate. Share state through external systems.

  • The exception is application events: publisher.broadcast(event)

delivers the event to every isolate exactly once (main relays worker broadcasts to the siblings), so isolates can react to each other — contrast with @Scheduled, which simply runs everywhere. See Application events.

  • Labeled experimental; server.isolates: 1 (the default) uses none of the

isolate machinery.

Profiles

Spring-style configuration profiles:

application.yaml            # base
application-dev.yaml        # overlay when 'dev' is active
application-prod.yaml       # overlay when 'prod' is active

Activate via the DIANA_PROFILE environment variable (comma-separated, later profiles win) or the diana.profile key in the base file — DIANA_PROFILE replaces the key entirely when set:

DIANA_PROFILE=prod,eu dart run bin/server.dart

Precedence (lowest → highest): base file → profile overlays in listed order → environment variables. A profile without a file is skipped. config.activeProfiles exposes the active list at runtime.

Deployment checklist

  • Configuration is env-overridable by design: server.port ← SERVER_PORT,

etc. — see the config keys reference.

  • Missing required keys (@Value without default, non-nullable

@ConfigurationProperties) fail at startup.

  • SIGTERM triggers graceful shutdown (drain → @PreDestroy) — Kubernetes

default termination works out of the box.

  • /actuator/health (when management.enabled) returns 503 while any

HealthIndicator is down — wire it to readiness probes.

JSON serialization

Diana gives you three interchangeable ways to serialize DTOs. Route adapters detect which one a class uses — at build time, with actionable errors.

Option 1 — @Json (recommended: zero boilerplate)

Annotate the class; Diana generates the codec into the part file and route adapters use it automatically. No fromJson, no toJson:

import 'package:diana/diana.dart';

part 'create_todo_request.diana.dart';

@Json()
class CreateTodoRequest {
  @NotBlank()                 // validation composes with @Json
  final String title;

  @JsonField(name: 'prio')    // rename the JSON key
  final int? priority;

  const CreateTodoRequest({required this.title, this.priority});
}

Supported field types: String, int, double, bool, num, dynamic, DateTime (ISO-8601), enums (by name), List<T> and Map<String, T> of supported types, nested @Json classes (codec-to-codec) or classes following the convention below — all optionally nullable. Anything else is a build error listing exactly this set.

Rules: part directive required; public unnamed constructor whose parameters match field names. Bodies that don't match the DTO shape (wrong types, missing keys, unknown enum values) become 400s, not 500s.

Generated names: $CreateTodoRequestFromJson / $CreateTodoRequestToJson — public, callable manually if needed.

Option 2 — hand-written convention

class TodoDto {
  final int id;
  const TodoDto({required this.id});

  factory TodoDto.fromJson(Map<String, dynamic> json) =>
      TodoDto(id: json['id'] as int);
  Map<String, dynamic> toJson() => {'id': id};
}

Full control; verified at build time (fromJson needed for @Body, toJson for returns).

Option 3 — json_serializable

Diana's .diana.dart part files coexist with json_serializable's .g.dart; one build_runner run drives both. The todoapi example keeps TodoDto on json_serializable precisely to prove the interop.

What routes accept and return

The full table of @Body parameter types (including String raw bodies and FormData uploads) and return types is in the controllers guide.

Manual JSON responses

DianaResponse.json(data) encodes with jsonEncode. Prefer explicit $XToJson(dto) / dto.toJson() for compile-time safety.

Testing

Diana applications test at three levels, all without mocking frameworks or special test kits: your classes are plain Dart, and the generated wiring is callable from tests.

1. Unit tests — plain Dart

Services, repositories, middleware and validators are ordinary classes. Construct them by hand:

test('service reports missing todos', () {
  final service = TodoService(InMemoryTodoRepository());
  expect(() => service.getOrThrow(99), throwsA(isA<TodoNotFoundError>()));
});

Middleware unit-test naturally thanks to the functional Next parameter:

test('guard rejects a missing api key', () async {
  final guard = ApiKeyMiddleware('secret');
  final response = await guard.handle(
    DianaRequest(method: HttpMethod.get, uri: Uri.parse('/x')),
    (req) async => const DianaResponse.text('reached handler'),
  );
  expect(response.statusCode, 401);
});

DianaRequest is directly constructible for tests — pass pathParameters, headers and a bodyReader as needed (see the runtime reference).

Generated validators are constants:

final result = const $CreateTodoRequestValidator()
    .validate(CreateTodoRequest(title: '  '));
expect(result.isValid, isFalse);

2. Wiring tests — the generated context

buildDianaContext({DianaConfig? config}) constructs the full DI graph without any HTTP:

test('the graph wires singletons', () {
  final ctx = buildDianaContext(
    config: DianaConfig({'app.greeting': 'hi'}),
  );
  expect(identical(ctx.todoService.repo, ctx.inMemoryTodoRepository), isTrue);
});

Because resolution happened at build time, this test mostly guards runtime behaviour (constructor side effects, config values) — a broken graph would not have compiled.

3. End-to-end tests — real HTTP

buildDianaServer() + serve(port: 0) boots the actual application on an OS-assigned port. Inject test configuration instead of relying on application.yaml:

import 'dart:convert';
import 'dart:io';

import 'package:diana/diana.dart';
import 'package:test/test.dart';
import 'package:todo_api/app.diana_app.dart';

void main() {
  late DianaServer server;
  late int port;

  setUpAll(() async {
    server = await buildDianaServer(
      config: DianaConfig({'app.apiKey': 'test-key'}),
    );
    await server.serve(port: 0, quiet: true);
    port = server.port!;
  });

  tearDownAll(() => server.close());

  Future<(int, dynamic)> get(String path) async {
    final client = HttpClient();
    try {
      final req =
          await client.getUrl(Uri.parse('http://127.0.0.1:$port$path'));
      final res = await req.close();
      final text = await res.transform(utf8.decoder).join();
      return (res.statusCode, text.isEmpty ? null : jsonDecode(text));
    } finally {
      client.close();
    }
  }

  test('binds path params and maps domain errors', () async {
    final (status, body) = await get('/todos/999');
    expect(status, 404);
    expect(body, containsPair('error', 'todo_not_found'));
  });
}

What to cover end-to-end (the example's suite is a template):

  • happy paths per route, including created/deleted state
  • binding failures (bad path param → 400, wrong content type → 415,

malformed JSON → 400)

  • validation failures (400 with the fields map)
  • middleware effects (short-circuit status codes, injected headers)
  • advice-mapped errors and the opaque 500 for unexpected ones

Annotation reference

Every annotation in package:diana_annotation (re-exported by package:diana/diana.dart). All annotations are const classes with no runtime behaviour — they exist for the generator.

Notation: [x] optional positional parameter, {x} named parameter.

Dependency injection

@Injectable({Scope scope = Scope.singleton, Type? as, String? name})

Target: class. Marks a class as a provider in the DI graph. Instantiated through its public unnamed generative constructor; every constructor parameter is resolved at build time.

Parameter Meaning
scope Lifecycle: Scope.singleton (default), Scope.request, Scope.transient.
as Explicitly bind this provider to a type it implements/extends, taking precedence over auto-binding candidates. Build error if the class doesn't implement it, or if two providers claim the same type.
name Qualifier. A named provider is only injectable through @Named(name).

@Service(...), @Repository(...), @Component(...)

Target: class. Semantic aliases of @Injectable with identical parameters and behaviour. Use them to communicate a class's role.

@Named(String name)

Target: constructor parameter. Selects the provider registered with qualifier name for this parameter.

Notifier(@Named('smtp') MailSender sender);

enum Scope { singleton, request, transient }

See scopes.

Web

@RestController([String path = '/', Scope scope = Scope.singleton])

Target: class. Declares an HTTP controller; all routes mount under path. The controller joins the DI graph with the given scope (a controller depending on request-scoped providers must itself be request-scoped). Requires a part '<file>.diana.dart'; directive in the library.

@Get, @Post, @Put, @Delete, @Patch — ([String path = ''])

Target: method (public, instance). Maps the method to the HTTP verb, at path relative to the controller ('' = the controller path itself). Paths use :name segments for path parameters.

@HttpRoute(String method, String path)

Target: method. Base class of the verb annotations; use directly for verbs without a shorthand: @HttpRoute('HEAD', '/status'). method is upper-case.

@PathParam([String? name])

Target: parameter. Binds a :name path segment. name defaults to the Dart parameter name. Type: non-nullable String/int/double/bool/num. Conversion failure → 400.

@QueryParam([String? name, String? defaultValue])

Target: parameter. Binds a query-string parameter. name defaults to the parameter name. defaultValue is written as a string ('20') and converted like a real value. A nullable parameter type makes it optional (bound to null when absent); a non-nullable type without default is required (400 when missing).

@Header([String? name])

Target: parameter. Binds a request header, case-insensitively. Same type/nullability rules as @QueryParam (no default value).

@Body()

Target: parameter. Binds the request body. Parameter types: a DTO (@Json, hand-written fromJson, or json_serializable), Map<String, dynamic>, List<Dto>, a List of JSON primitives, String (raw text, any content type) or FormData (multipart / urlencoded — see uploads). Wrong content type → 415; malformed/mis-shaped bodies → 400; oversized multipart → 413. DTO validators run before the handler.

@ResponseStatus(int code)

Target: method. Overrides the success status code (e.g. 201). Applies to JSON, text and void returns; ignored when the method returns DianaResponse (which carries its own status).

@CrossOrigin({origins, methods, headers, exposedHeaders, credentials, maxAge})

Target: class (controller) or method (route). Enables CORS with a policy that fully replaces the global server.cors.* configuration (route > controller > global). Diana registers the OPTIONS preflight automatically. Fields mirror the config keys — see CORS.

@Consumes(List<String> mimeTypes)

Target: class (controller) or method (route); method replaces controller entirely. Restricts the request content types the route accepts; the body is decoded with the matching registered BodyCodec (other content types → 415). The listed set replaces the JSON default. Requires a codec-decoded @Body parameter (Map, List or DTO). See Content negotiation.

@Produces(List<String> mimeTypes)

Target: class (controller) or method (route); method replaces controller entirely. Declares the response formats the route can produce; the response is encoded with the first type the request's Accept header allows (server preference order; nothing acceptable → 406). Applies to JSON-encodable returns only; cannot be combined with Stream returns. See Content negotiation.

Lifecycle

@PostConstruct() / @PreDestroy()

Target: method (public instance, no parameters, void/Future<void>; at most one of each per class; singleton providers only). Run after construction during initialize() (dependency order) and during graceful shutdown in dispose() (reverse order). See the lifecycle guide.

Scheduling

@Scheduled({int? fixedRate, int? fixedDelay, int initialDelay = 0})

Target: method (same signature rules as lifecycle hooks; singleton providers only). Exactly one of fixedRate/fixedDelay (milliseconds). Tasks start after initialization and stop on shutdown; fixedRate skips overlapping ticks, fixedDelay re-arms after completion. See Observability.

Events

@EventListener()

Target: method (public instance, exactly one positional parameter — the event type, a non-nullable class — returning void/Future<void>; singleton providers only). Registers the method as an application-event listener: it receives every event published through DianaEventPublisher whose type matches the parameter (subtypes included). Listeners are registered before initialize(), dispatched in registration order and awaited. See the events guide.

Authentication & authorization

These require the diana_auth package (the runtime types they wire in live there). See the auth guide.

@Secured()

Target: class (REST/WebSocket controller or gRPC service) or route method; method replaces controller. Requires an authenticated principal — anonymous requests get 401. The generator appends a guard after the authentication middleware.

@RolesAllowed(List<String> roles)

Target: same as @Secured. Requires the principal to hold any of roles (401 anonymous, 403 authenticated-but-missing-role). Implies @Secured.

@Principal()

Target: route-method parameter. Binds the authenticated principal (AuthPrincipal or a subclass). A non-nullable parameter throws 401 when unauthenticated; a nullable one receives null.

JSON

@Json()

Target: class. Generates $XFromJson/$XToJson into the class's part file; route adapters use them automatically for @Body parameters and return values — no fromJson/toJson boilerplate. Supported field types are listed in the JSON guide. Requires a part directive and a public unnamed constructor whose parameters match field names.

@JsonField({String? name})

Target: field (inside a @Json class). Renames the field's JSON key.

WebSockets

@WebSocketController(String path, [Scope scope = Scope.singleton])

Target: class (must implement WebSocketHandler, e.g. by extending BaseWebSocketHandler). Registers the class as a WebSocket endpoint at path (which may contain :name parameters, exposed via WebSocketSession.pathParameters). The class joins the DI graph:

  • Scope.singleton (default) — one shared handler for all connections.
  • Scope.transient — a fresh handler per connection.
  • Scope.request — build error (not applicable to WebSockets).

Endpoint paths must be unique across the application. @UseMiddleware on the class runs as handshake interceptors (blocking the upgrade on short-circuit and propagating request attributes into the session); global middleware and @ControllerAdvice do not apply to socket traffic. See the WebSockets guide.

gRPC

@GrpcService()

Target: class (must extend a protoc-generated XServiceBase, i.e. a package:grpc Service). Registers the class as a gRPC service: it joins the DI graph as a singleton (constructor injection, @Value, lifecycle apply) and the generated DianaApp serves all @GrpcService classes on grpc.port through package:diana_grpc (a dependency your app must declare). Cannot be combined with other role annotations. See the gRPC guide.

Persistence

Requires the diana_data package (the Database it works with lives there). See the persistence guide.

@Transactional()

Target: method (must return Future) or class (all public Future-returning methods) on a @Service/@Component/@Repository provider that is extendable (not final/base/sealed). Runs the method inside a database transaction via a generated proxy subclass. Nesting joins the enclosing transaction as a savepoint (propagation REQUIRED); an uncaught exception rolls back and rethrows.

Middleware

@GlobalMiddleware({int order = 0})

Target: class (must implement Middleware). Registers the class as global middleware applied to every route, and makes it an injectable singleton. Lower order runs first (outermost); ties break by class name.

@UseMiddleware(List<Type> middleware)

Target: class (controller) or method (route). Applies the listed middleware — in order — to all routes of a controller or to one route. Each type must be an injectable singleton implementing Middleware (verified at build time). Effective order: global → controller-level → route-level.

Configuration

@Value(String key, {Object? defaultValue})

Target: constructor parameter (of any injectable class). Injects the configuration value at key (dot notation). The parameter type must be String/int/double/bool/num. defaultValue must be a String/int/double/bool literal. Without a default, a missing key fails at startup.

@ConfigurationProperties(String prefix)

Target: class. Binds a configuration section to the class: each constructor parameter is read from <prefix>.<paramName> (nullable parameter ⇒ optional key). The class becomes an injectable singleton. Parameter types: String/int/double/bool/num (nullable allowed). Requires a part directive (the binder function is generated).

Exception handling

@ControllerAdvice()

Target: class. Declares a global exception-handling component (an injectable singleton). Must contain at least one @ExceptionHandler method.

@ExceptionHandler(Type exception)

Target: method (inside a @ControllerAdvice class). Handles thrown exceptions of exception and its subtypes. When several handlers match, the most specific exception type wins.

Valid signatures — the first parameter type must be exactly the annotated type:

DianaResponse on(MyError e)
DianaResponse on(MyError e, DianaRequest req)
Future<DianaResponse> on(MyError e)              // async also allowed

Validation

All validation annotations target fields of DTO classes and accept an optional {String? message} overriding the default text. All except @NotNull skip null values. Wrong field type ⇒ build error.

@NotNull({String? message})

Any field. Fails when the value is null.

@NotEmpty({String? message})

String, List, Set or Map. Fails when empty.

@NotBlank({String? message})

String. Fails when empty or whitespace-only.

@Min(num value, {String? message}) / @Max(num value, {String? message})

Numeric fields. Fail when < value / > value.

@Size({int? min, int? max, String? message})

String, List, Set or Map. Fails when the length is outside [min, max] (either bound optional).

@Pattern(String regex, {String? message})

String. Fails when the value doesn't match regex. Note: in files importing Diana, Pattern shadows dart:core's Pattern (mirroring Jakarta's @Pattern); use an import prefix if you need the core type.

@Email({String? message})
